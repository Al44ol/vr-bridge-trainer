### 0.1. Платформа

Unity 6000.4.6f1, URP 17.4 (Render Graph), линейное цветовое пространство; OpenXR 1.16.1, XR Interaction Toolkit 3.4.1. Целевое оборудование: Meta Quest 3, работающий как PC-VR шлем через Virtual Desktop, частота 90 Гц (бюджет кадра 11,1 мс); учебные станции с RTX 5070 Ti.

### 0.2. Плавающее начало координат (A1)

**Проблема.** Одинарная точность float (24 бита мантиссы) на удалении 10 км даёт шаг представления около 1 мм, а на 100 км — около 8 мм. Это вызывает дрожание геометрии и камеры в VR, где заметны даже миллиметровые рывки.

**Решение.** Судно и наблюдатель всегда находятся около начала координат сцены. Истинная позиция судна хранится в двойной точности: `WorldPosition {double East, North}`, метры. Объекты мира ставятся в сцену через преобразование `p_сцены = p_мира − p_судна`. Система координат: +X — восток, +Z — север.

**Вода.** Фазы волн считаются на CPU в double как `φ = k·(d·p_судна) − ω·t (mod 2π)` и передаются в шейдер, поэтому смещение мира не накапливает погрешность.

### 0.3. Модель движения судна (A2)

Обозначения: ψ — курс (0 = N, по часовой); r — угловая скорость; u — скорость хода; δ — перекладка руля (> 0 — правый борт); L — длина судна; SF — положение телеграфа (−1…1).

1. **Рулевая машина.** dδ/dt = clamp((δ_зад − δ)/dt, −ω_δ, +ω_δ), |δ| ≤ δ_max. По СОЛАС гл. II-1, правило 29, перекладка с 35° одного борта на 30° другого занимает не более 28 с, поэтому ω_δ = 65°/28 с ≈ 2,32 °/с.
2. **Скорость.** du/dt = (u_зад − u)/τ.
   - u_зад = SF·V_эксп при SF ≥ 0 и SF·V_эксп·k_зх при SF < 0.
   - τ = τ_разг при разгоне и τ_торм при торможении.
   - Дискретизация точная: u(t+Δt) = u_зад + (u − u_зад)·e^(−Δt/τ).
3. **Поворот — модель Номото 1-го порядка.** T·ṙ + r = K·δ, где K = K'·U/L и T = T'·L/U.
   - Точная дискретизация: r(t+Δt) = Kδ + (r − Kδ)·e^(−Δt/T).
   - Диаметр установившейся циркуляции D = 2L/(K'·δ) не зависит от скорости.
4. **Кинематика** (в double): ψ += r·Δt, E += u·sin ψ·Δt, N += u·cos ψ·Δt.
5. **Шаг интегрирования.** FixedUpdate, Δt = 0,02 с (50 Гц). Отображение интерполируется к 90 Гц: α = (t − t_fixed)/Δt.

### 0.4. Морская поверхность (A1)

- **Геометрия.** Радиальный меш радиусом 10 км, около 98 тыс. вершин, со сгущением к центру.
- **Крупные волны.** Четыре волны Герстнера (λ = 90/45/20/9 м) веером вокруг направления ветра. Амплитуда a_i = a_i⁰·I^{n_i}, где I — интенсивность волнения пресета погоды. Дисперсия глубокой воды: ω = √(g·k).
- **Рябь.** Ещё четыре мелкие волны (λ = 4,1…0,75 м) только в нормалях, без смещения вершин.
- **Затухание.** Волны гаснут на 1,5…6 км; волны мельче шага сетки или размера пикселя подавляются, чтобы не было алиасинга.
- **Пена.** Барашки — по крутизне гребня Σ k·a·sin φ. За кормой — кильватерный след с углом Кельвина 19,47°.
- **Качка.** Пока кинематическая — сумма синусоид, с волнами не связана (запрос 4).

## 1. Технический долг: Single Pass Instanced, дождь, правила журнала (запрос 1)

### 1.1. Переход OpenXR с Multi-pass на Single Pass Instanced

**Что сделано.** Режим стереорендеринга для PC (Standalone) переключён с Multi-pass на Single Pass Instanced (SPI) через новый пункт меню `Tools/VR Bridge/OpenXR Render Mode`. Пункт оставлен двусторонним: оба режима можно сравнить на одной сцене.

**Обоснование.**
- **Multi-pass.** Сцена проходится дважды, по разу на каждый глаз: удваиваются отсечение, сортировка, отправка вызовов отрисовки (draw calls) и смена состояний на CPU.
- **SPI.** Каждый объект рисуется один раз с инстансингом ×2 в текстурный массив из двух слоёв. Номер глаза (`unity_StereoEyeIndex`) выбирается по `SV_InstanceID`, вершинный шейдер берёт свою матрицу вида-проекции для каждого глаза.
- **Ожидаемый эффект.** Число вызовов отрисовки и SetPass-вызовов уменьшается примерно вдвое. Для GPU выигрыш меньше: растеризуется столько же пикселей, но меньше переключений состояния и повторной обработки геометрии.

**Тонкость Play Mode.** Тренажёр проверяется в Play Mode через Virtual Desktop, а активная платформа проекта — Android. При этом OpenXR в Play Mode берёт настройки Standalone (`OpenXRSettings.GetInstance`: в редакторе — `BuildTargetGroup.Standalone`). Поэтому переключался именно режим Standalone; для Android SPI был включён и раньше.

**Проверка шейдеров.**

| Шейдер | Назначение | Поддержка SPI | Изменения |
|---|---|---|---|
| `VRBridgeTrainer/OceanSurface` | вода | полная¹ | не потребовались |
| `VRBridgeTrainer/SkyboxHorizonFog` | небо | полная² | не потребовались |
| URP Lit, URP Particles/Unlit | судно, мостик, дождь | встроенная | — |
| TextMesh Pro, шейдеры XRI/VR Template | интерфейс, руки | встроенная | не трогаем |

¹ В шейдере воды есть `#pragma multi_compile_instancing`, `UNITY_VERTEX_INPUT_INSTANCE_ID` во входной и выходной структурах, `UNITY_VERTEX_OUTPUT_STEREO`, `UNITY_SETUP_INSTANCE_ID` / `UNITY_TRANSFER_INSTANCE_ID` / `UNITY_INITIALIZE_VERTEX_OUTPUT_STEREO` в вершинной программе и `UNITY_SETUP_STEREO_EYE_INDEX_POST_VERTEX` во фрагментной. Положение камеры берётся через `GetWorldSpaceNormalizeViewDir`, то есть через `_WorldSpaceCameraPos`, который в SPI свой для каждого глаза. Текстуры экрана и глубины не используются: вода прозрачная, ZWrite Off.

² Шейдер неба: те же макросы, кроме передачи instance ID во фрагментную программу. Она там не нужна, так как фрагмент зависит только от направления взгляда.

Подавление мелких волн по `ddx`/`ddy` в SPI вычисляется для каждого глаза отдельно. Ракурсы глаз почти совпадают, поэтому заметной разницы между глазами нет.

**Методика замера производительности.**
- **Инструмент.** `FrameTimingCapture` (объект `PerfCapture`), запуск — F8.
- **Что пишется для каждого кадра:**
  - время кадра CPU и GPU (`FrameTimingManager`; требуется Player Settings → Frame Timing Stats);
  - реальный интервал кадра;
  - число вызовов отрисовки, SetPass и батчей (`ProfilerRecorder`).
- **Условия замера:**
  - сцена BridgeScene, пресет «волнение», судно на стопе;
  - голова в фиксированном положении: на рабочем месте, взгляд вперёд по носу;
  - прогрев 2 с, затем 30 с;
  - 3 прогона на режим.
- **Файлы.** `ThesisData/Performance/frametiming_<режим>_<дата>.csv` — покадрово. `frametiming_summary.csv` — сводка по замерам: среднее, медиана, p95, p99, доля кадров дольше 11,1 мс × 1,05.
- **Контроль.** Frame Debugger: в SPI вызовы помечены как stereo instanced, их вдвое меньше. Profiler → GPU Usage — если `FrameTimingManager` вернёт 0 для GPU.

**Наблюдение.** В Play Mode кадр ограничен процессором (CPU 12,2 мс против GPU 3,9 мс): GPU загружен примерно на треть бюджета. SPI в первую очередь сокращает работу CPU по отправке вызовов отрисовки, поэтому главный ожидаемый эффект перехода — рост частоты кадров и снижение CPU-времени, а не GPU-времени. Счётчик Draw Calls через `ProfilerRecorder` в редакторе недоступен (−1); число вызовов берётся из Frame Debugger.

**Ограничения методики.** В Play Mode редактор дополнительно рисует окно Game и интерфейс редактора, поэтому абсолютные значения выше, чем в сборке. Корректно сравнивать только режимы между собой при одинаковых условиях. Virtual Desktop кодирует видео на том же GPU (аппаратный кодер). Это может влиять на общую загрузку, поэтому оба режима измеряются при одинаковых настройках Virtual Desktop: разрешение, битрейт, кодек.

### 1.2. Дождь в шторм

**Что сделано.** Компонент `RainEffect` переписан и подключён к `WeatherController`. Дождь идёт только в пресете «шторм», появляется и исчезает плавно вместе со сменой погоды и не проникает в рубку.

**Связь с погодой.** В пресет погоды добавлен параметр интенсивности дождя R ∈ [0; 1]: шторм — 1, остальные пресеты — 0. При смене пресета R интерполируется так же, как свет, туман и волнение: R(t) = R₀ + (R₁ − R₀)·s(t/τ_п), где s(x) = 3x² − 2x³ (SmoothStep), τ_п = 3 с. Частота появления капель: ṅ = ṅ_max·R.

**Привязка к судну при плавающем начале координат.** Судно неподвижно в начале сцены, а мир «течёт» мимо него. Поэтому:
- частицы считаются в мировом пространстве сцены, которое в каждый момент совпадает с горизонтальной системой судна;
- излучатель ставится над камерой каждый кадр и не является дочерним к качающемуся корпусу, иначе дождь наклонялся бы при крене;
- движение судна задаётся в скорости капель явно.

Скорость капли относительно судна:

  **v** = **v**_ветра − **v**_судна + (0, −w, 0),

- **v**_ветра = U_w·**d**_ветра. Капля быстро принимает горизонтальную скорость воздуха; направление ветра то же, что у волн (`OceanWaves.windFromDeg`).
- **v**_судна = u·**e**_нос, где **e**_нос — горизонтальная проекция оси носа.
- w — установившаяся скорость падения капли.

В результате на ходу дождь заметно сносится в корму, а при смене курса меняется угол косого дождя.

Чтобы капли приходили к наблюдателю, а не мимо, излучатель смещён против относительного ветра на **v**_гор·h/w, где h — высота излучения. Время жизни капли: t_ж = (y_кам + h − y_min)/w, где y_min = max(y_кам − Δ, y_воды).

**Защита рубки.**
- **Способ.** Модуль Trigger системы частиц уничтожает капли, попавшие в объём рубки. Объём — BoxCollider-триггер `RainShelter`, дочерний к Ship, поэтому качается вместе с рубкой. Капля долетает до крыши или окна и исчезает; снаружи за стёклами дождь виден.
- **Сравнение вариантов:**
  - Collision с коллайдерами крыши — дороже по CPU и требует коллайдеров у модели мостика; зато даёт брызги, это задел на будущее;
  - маска по буферу глубины — сложнее в SPI и при прозрачной воде;
  - триггер-объём — одна проверка «точка в коробке» на частицу, не зависит от геометрии модели.
- **Взаимодействие с XR.** Триггер на слое Ignore Raycast не мешает лучам: XRI по умолчанию игнорирует триггеры (`QueryTriggerInteraction.Ignore`).

**Порядок отрисовки.** Вода прозрачная (очередь 3000, без записи глубины), капли — 3100, то есть всегда после воды.

**Сборка.** Материал капель — ассет `Rain.mat`, а не `Shader.Find` в рантайме, иначе шейдер частиц мог быть вырезан из сборки.

**Состояние на 10.10.2026: отложено.** Логика работает: по логу при шторме дождь включается, в воздухе около 3900 из 6000 частиц, часть уничтожается объёмом рубки. Но в шлеме капли не видны ни из рубки, ни снаружи. Найдены и исправлены две причины:
1. Ошибка генерации текстуры: `Mathf.SmoothStep(a, b, t)` в Unity интерполирует между a и b, а не работает как шейдерный smoothstep, поэтому непрозрачность центра капли была 0,2.
2. Очередь отрисовки: URP сбросил очередь материала в 3000 — ту же, что у воды без записи глубины.

После исправлений `Setup Rain` ещё не перезапускался, проверка будет позже. Возможные дальнейшие шаги: проверить кадр в Frame Debugger (рисуются ли частицы), временно отключить `RainShelter`, увеличить толщину капли.

**Ограничения.**
- Плотность капель стилизована: около 0,3 капли/м³ в видимом объёме против сотен в реальном ливне. Задача — визуальный признак условий, а не физическая модель осадков.
- Снижение видимости в шторм обеспечивает туман пресета (плотность 0,025), а не дождь.
- Капли не оставляют следов на стёклах; дворников и брызг нет.
- Скорость ветра постоянна и не связана с моделью судна: ветер на дрейф пока не влияет (A2).
- Объём рубки задан коробкой и подгоняется вручную. Открытые крылья мостика, если войдут в коробку, тоже окажутся «сухими».
