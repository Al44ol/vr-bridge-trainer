### 0.2. Плавающее начало координат (A1)

**Проблема.** Одинарная точность float (24 бита мантиссы) на удалении 10 км даёт шаг представления около 1 мм, а на 100 км — около 8 мм. Это вызывает дрожание геометрии и камеры в VR, где заметны даже миллиметровые рывки.

**Решение.** Судно и наблюдатель всегда находятся около начала координат сцены. Истинная позиция судна хранится в двойной точности: `WorldPosition {double East, North}`, метры. Объекты мира ставятся в сцену через преобразование `p_сцены = p_мира − p_судна`. Система координат: +X — восток, +Z — север.

**Вода.** Фазы волн считаются на CPU в double как `φ = k·(d·p_судна) − ω·t (mod 2π)` и передаются в шейдер, поэтому смещение мира не накапливает погрешность.

### 0.3. Модель движения судна (A2)

Обозначения: ψ — курс (0 = N, по часовой); r — угловая скорость; u — скорость хода; δ — перекладка руля (> 0 — правый борт); L — длина судна; SF — положение телеграфа (−1…1).

1. **Рулевая машина.** dδ/dt = clamp((δ_зад − δ)/dt, −ω_δ, +ω_δ), |δ| ≤ δ_max. По СОЛАС гл. II-1, правило 29, перекладка с 35° одного борта на 30° другого занимает не более 28 с, поэтому ω_δ = 65°/28 с ≈ 2,32 °/с.
2. **Скорость.** du/dt = (u_зад − u)/τ.
   - u_зад = SF·V_эксп при SF ≥ 0 и SF·V_эксп·k_зх при SF < 0.
   - τ = τ_разг при разгоне и τ_торм при торможении.
   - Дискретизация точная: u(t+Δt) = u_зад + (u − u_зад)·e^(−Δt/τ).
3. **Поворот — модель Номото 1-го порядка.** T·ṙ + r = K·δ, где K = K'·U/L и T = T'·L/U.
   - Точная дискретизация: r(t+Δt) = Kδ + (r − Kδ)·e^(−Δt/T).
   - Диаметр установившейся циркуляции D = 2L/(K'·δ) не зависит от скорости.
4. **Кинематика** (в double): ψ += r·Δt, E += u·sin ψ·Δt, N += u·cos ψ·Δt.
5. **Шаг интегрирования.** FixedUpdate, Δt = 0,02 с (50 Гц). Отображение интерполируется к 90 Гц: α = (t − t_fixed)/Δt.

### 0.4. Морская поверхность (A1)

- **Геометрия.** Радиальный меш радиусом 10 км, около 98 тыс. вершин, со сгущением к центру.
- **Крупные волны.** Четыре волны Герстнера (λ = 90/45/20/9 м) веером вокруг направления ветра. Амплитуда a_i = a_i⁰·I^{n_i}, где I — интенсивность волнения пресета погоды. Дисперсия глубокой воды: ω = √(g·k).
- **Рябь.** Ещё четыре мелкие волны (λ = 4,1…0,75 м) только в нормалях, без смещения вершин.
- **Затухание.** Волны гаснут на 1,5…6 км; волны мельче шага сетки или размера пикселя подавляются, чтобы не было алиасинга.
- **Пена.** Барашки — по крутизне гребня Σ k·a·sin φ. За кормой — кильватерный след с углом Кельвина 19,47°.
- **Качка.** Пока кинематическая — сумма синусоид, с волнами не связана (с запроса 4 — на волнах, раздел 4).

## 1. Технический долг: Single Pass Instanced, дождь, правила журнала (запрос 1)

### 1.1. Переход OpenXR с Multi-pass на Single Pass Instanced

**Что сделано.** Режим стереорендеринга для PC (Standalone) переключён с Multi-pass на Single Pass Instanced (SPI) через новый пункт меню `Tools/VR Bridge/OpenXR Render Mode`. Пункт оставлен двусторонним: оба режима можно сравнить на одной сцене.

**Обоснование.**
- **Multi-pass.** Сцена проходится дважды, по разу на каждый глаз: удваиваются отсечение, сортировка, отправка вызовов отрисовки (draw calls) и смена состояний на CPU.
- **SPI.** Каждый объект рисуется один раз с инстансингом ×2 в текстурный массив из двух слоёв. Номер глаза (`unity_StereoEyeIndex`) выбирается по `SV_InstanceID`, вершинный шейдер берёт свою матрицу вида-проекции для каждого глаза.
- **Ожидаемый эффект.** Число вызовов отрисовки и SetPass-вызовов уменьшается примерно вдвое. Для GPU выигрыш меньше: растеризуется столько же пикселей, но меньше переключений состояния и повторной обработки геометрии.

**Тонкость Play Mode.** Тренажёр проверяется в Play Mode через Virtual Desktop, а активная платформа проекта — Android. При этом OpenXR в Play Mode берёт настройки Standalone (`OpenXRSettings.GetInstance`: в редакторе — `BuildTargetGroup.Standalone`). Поэтому переключался именно режим Standalone; для Android SPI был включён и раньше.

**Проверка шейдеров.**

| Шейдер | Назначение | Поддержка SPI | Изменения |
|---|---|---|---|
| `VRBridgeTrainer/OceanSurface` | вода | полная¹ | не потребовались |
| `VRBridgeTrainer/SkyboxHorizonFog` | небо | полная² | не потребовались |
| URP Lit, URP Particles/Unlit | судно, мостик, дождь | встроенная | — |
| TextMesh Pro, шейдеры XRI/VR Template | интерфейс, руки | встроенная | не трогаем |

¹ В шейдере воды есть `#pragma multi_compile_instancing`, `UNITY_VERTEX_INPUT_INSTANCE_ID` во входной и выходной структурах, `UNITY_VERTEX_OUTPUT_STEREO`, `UNITY_SETUP_INSTANCE_ID` / `UNITY_TRANSFER_INSTANCE_ID` / `UNITY_INITIALIZE_VERTEX_OUTPUT_STEREO` в вершинной программе и `UNITY_SETUP_STEREO_EYE_INDEX_POST_VERTEX` во фрагментной. Положение камеры берётся через `GetWorldSpaceNormalizeViewDir`, то есть через `_WorldSpaceCameraPos`, который в SPI свой для каждого глаза. Текстуры экрана и глубины не используются: вода прозрачная, ZWrite Off.

² Шейдер неба: те же макросы, кроме передачи instance ID во фрагментную программу. Она там не нужна, так как фрагмент зависит только от направления взгляда.

Подавление мелких волн по `ddx`/`ddy` в SPI вычисляется для каждого глаза отдельно. Ракурсы глаз почти совпадают, поэтому заметной разницы между глазами нет.

**Методика замера производительности.**
- **Инструмент.** `FrameTimingCapture` (объект `PerfCapture`), запуск — F8.
- **Что пишется для каждого кадра:**
  - время кадра CPU и GPU (`FrameTimingManager`; требуется Player Settings → Frame Timing Stats);
  - реальный интервал кадра;
  - число вызовов отрисовки, SetPass и батчей (`ProfilerRecorder`).
- **Условия замера:**
  - сцена BridgeScene, пресет «волнение», судно на стопе;
  - голова в фиксированном положении: на рабочем месте, взгляд вперёд по носу;
  - прогрев 2 с, затем 30 с;
  - 3 прогона на режим.
- **Файлы.** `ThesisData/Performance/frametiming_<режим>_<дата>.csv` — покадрово. `frametiming_summary.csv` — сводка по замерам: среднее, медиана, p95, p99, доля кадров дольше 11,1 мс × 1,05.
- **Контроль.** Frame Debugger: в SPI вызовы помечены как stereo instanced, их вдвое меньше. Profiler → GPU Usage — если `FrameTimingManager` вернёт 0 для GPU.

Для итоговой таблицы ВКР желательно по 3 прогона на режим в одном пресете при одном ракурсе. Счётчик Draw Calls через `ProfilerRecorder` в редакторе недоступен (−1); при необходимости число вызовов берётся из Frame Debugger.

**Ограничения методики.** В Play Mode редактор дополнительно рисует окно Game и интерфейс редактора, поэтому абсолютные значения выше, чем в сборке. Корректно сравнивать только режимы между собой при одинаковых условиях. Virtual Desktop кодирует видео на том же GPU (аппаратный кодер). Это может влиять на общую загрузку, поэтому оба режима измеряются при одинаковых настройках Virtual Desktop: разрешение, битрейт, кодек.

### 1.2. Дождь в шторм

**Что сделано.** Компонент `RainEffect` переписан и подключён к `WeatherController`. Дождь идёт только в пресете «шторм», появляется и исчезает плавно вместе со сменой погоды и не проникает в рубку.

**Связь с погодой.** В пресет погоды добавлен параметр интенсивности дождя R ∈ [0; 1]: шторм — 1, остальные пресеты — 0. При смене пресета R интерполируется так же, как свет, туман и волнение: R(t) = R₀ + (R₁ − R₀)·s(t/τ_п), где s(x) = 3x² − 2x³ (SmoothStep), τ_п = 3 с. Частота появления капель: ṅ = ṅ_max·R.

**Привязка к судну при плавающем начале координат.** Судно неподвижно в начале сцены, а мир «течёт» мимо него. Поэтому:
- частицы считаются в мировом пространстве сцены, которое в каждый момент совпадает с горизонтальной системой судна;
- излучатель ставится над камерой каждый кадр и не является дочерним к качающемуся корпусу, иначе дождь наклонялся бы при крене;
- движение судна задаётся в скорости капель явно.

Скорость капли относительно судна:

  **v** = **v**_ветра − **v**_судна + (0, −w, 0),

- **v**_ветра = U_w·**d**_ветра. Капля быстро принимает горизонтальную скорость воздуха; направление ветра то же, что у волн (`OceanWaves.windFromDeg`).
- **v**_судна = u·**e**_нос, где **e**_нос — горизонтальная проекция оси носа.
- w — установившаяся скорость падения капли.

В результате на ходу дождь заметно сносится в корму, а при смене курса меняется угол косого дождя.

Чтобы капли приходили к наблюдателю, а не мимо, излучатель смещён против относительного ветра на **v**_гор·h/w, где h — высота излучения. Время жизни капли: t_ж = (y_кам + h − y_min)/w, где y_min = max(y_кам − Δ, y_воды).

**Защита рубки.**
- **Способ.** Модуль Trigger системы частиц уничтожает капли, попавшие в объём рубки. Объём — BoxCollider-триггер `RainShelter`, дочерний к Ship, поэтому качается вместе с рубкой. Капля долетает до крыши или окна и исчезает; снаружи за стёклами дождь виден.
- **Сравнение вариантов:**
  - Collision с коллайдерами крыши — дороже по CPU и требует коллайдеров у модели мостика; зато даёт брызги, это задел на будущее;
  - маска по буферу глубины — сложнее в SPI и при прозрачной воде;
  - триггер-объём — одна проверка «точка в коробке» на частицу, не зависит от геометрии модели.
- **Взаимодействие с XR.** Триггер на слое Ignore Raycast не мешает лучам: XRI по умолчанию игнорирует триггеры (`QueryTriggerInteraction.Ignore`).

**Порядок отрисовки.** Вода прозрачная (очередь 3000, без записи глубины), капли — 3100, то есть всегда после воды.

**Сборка.** Материал капель — ассет `Rain.mat`, а не `Shader.Find` в рантайме, иначе шейдер частиц мог быть вырезан из сборки.

**Состояние на 10.10.2026: отложено.** Логика работает: по логу при шторме дождь включается, в воздухе около 3900 из 6000 частиц, часть уничтожается объёмом рубки. Но в шлеме капли не видны ни из рубки, ни снаружи. Найдены и исправлены две причины:
1. Ошибка генерации текстуры: `Mathf.SmoothStep(a, b, t)` в Unity интерполирует между a и b, а не работает как шейдерный smoothstep, поэтому непрозрачность центра капли была 0,2.
2. Очередь отрисовки: URP сбросил очередь материала в 3000 — ту же, что у воды без записи глубины.

После исправлений `Setup Rain` ещё не перезапускался, проверка будет позже. Возможные дальнейшие шаги: проверить кадр в Frame Debugger (рисуются ли частицы), временно отключить `RainShelter`, увеличить толщину капли.

**Ограничения.**
- Плотность капель стилизована: около 0,3 капли/м³ в видимом объёме против сотен в реальном ливне. Задача — визуальный признак условий, а не физическая модель осадков.
- Снижение видимости в шторм обеспечивает туман пресета (плотность 0,025), а не дождь.
- Капли не оставляют следов на стёклах; дворников и брызг нет.
- Скорость ветра постоянна и не связана с моделью судна: ветер на дрейф пока не влияет (A2).
- Объём рубки задан коробкой и подгоняется вручную. Открытые крылья мостика, если войдут в коробку, тоже окажутся «сухими».

## 2. Стенд манёвренных испытаний (запрос 2, A3 — часть 1)

### 2.1. Выделение модели в отдельный модуль

**Что сделано.**
- Уравнения движения перенесены из компонента сцены `ShipNavigation` в класс `ShipDynamicsModel` на чистом C#. Класс не зависит от сцены, игрового цикла и Play Mode.
- Модель вместе с параметрами `ShipParameters` вынесена в отдельную сборку `VRBridge.Core`.
- Один и тот же код модели теперь используют:
  - тренажёр в реальном времени (`ShipNavigation`, шаг FixedUpdate);
  - стенд испытаний (без Play Mode);
  - автоматические тесты.

  Так исключено расхождение между «моделью для испытаний» и «моделью в шлеме».

**Проверка эквивалентности.** Тест `Refactor_MatchesLegacyStep_BitForBit` сравнивает новую модель с дословной копией прежнего шага интегрирования.
- Условия: 5 прогонов по 10 000 шагов, dt = 0,02 с, случайные команды руля от −40° до +40° (включая выход за δ_max) и положения телеграфа.
- Результат: курс, угловая скорость, скорость, угол руля и координаты совпадают точно, с допуском 0.

**Исправление, найденное при тестировании.** В прежней версии коэффициент усиления считался как K = K'·sign(u)·max(|u|, U_min)/L. При остановленном судне (|u| < U_min = 0,05 м/с) K не обнулялся, и переложенный руль медленно разворачивал судно на месте: около 6° за 10 мин при L = 150 м. Это физически неверно и противоречит самой модели (r_уст ∝ u).
- **Исправление:** K = K'·u/L по фактической скорости; U_min оставлен только в T = T'·L/U как защита от деления на ноль.
- **Область изменения:** при |u| ≥ U_min результат совпадает с прежним бит в бит, поэтому поведение на ходу не изменилось.
- **Проверка:** тест `Stopped_RudderDoesNotTurnShip` — на стопе с рулём 35° за 600 с курс меняется меньше чем на 1°.

### 3.2. Эталонная модель Mariner

Модель Абковица [13] с тремя степенями свободы: продольная u, поперечная v, рыскание r.

    m'₁₁·u̇' = X'(u', v', r', δ),
    [m'₂₂ m'₂₃; m'₃₂ m'₃₃]·[v̇'; ṙ'] = [Y'; N'](u', v', r', δ),

- X', Y', N' — полиномы до 3-й степени с 50 коэффициентами;
- m'₂₂ = m' − Y'_v̇, m'₂₃ = m'·x'_G − Y'_ṙ, m'₃₂ = m'·x'_G − N'_v̇, m'₃₃ = I'_z − N'_ṙ;
- безразмерные величины: u' = Δu/U, v' = v/U, r' = r·L/U, время t' = t·U/L.

Коэффициенты и уравнения перенесены дословно из открытой реализации MSS [1] (файл `mariner.m`, ссылка на [2]) в класс `MarinerModel` (сборка `VRBridge.Core`).

Отличия переноса от `mariner.m`:
- интегрирование RK4 с шагом dt = 0,02 с;
- знак руля: δ > 0 — правый борт, как в тренажёре;
- переключатель `PropellerAsymmetry` для постоянных членов Y'₀, N'₀ (п. 3.2.3).

Рулевая машина эталона: δ̇ = δ_зад − δ (апериодическое звено, T = 1 с), |δ̇| ≤ 5 °/с, |δ| ≤ 40°. Обороты винта постоянны, телеграфа нет. Поэтому торможение и разгон эталоном не описываются.

**3.2.1. Проверка переноса.**
- При δ = 0 и выключенной асимметрии скорость за 600 с остаётся равной U0 = 7,7175 м/с (точность 10⁻⁹), курс — нулевым.
- Без асимметрии циркуляции на ПБ и ЛБ симметричны (точность 10⁻⁶).

**3.2.2. Линеаризация и ширина линейной области.** При Δu = 0 линейная подсистема (v', r') даёт передаточную функцию Номото 2-го порядка [14]:

    r'/δ = K'·(1 + T'₃·s)/((1 + T'₁·s)(1 + T'₂·s)),   T' ≈ T'₁ + T'₂ − T'₃.

Для Mariner: **K' = 3,858; T'₁ = 5,658; T'₂ = 0,372; T'₃ = 0,889; T' = 5,141.** Линеаризация проверена численно: при δ = 0,02° установившееся r' отличается от K'·δ на 0,01 %.

Линейная область оказалась очень узкой — следствие больших нелинейных членов N'_vvr, Y'_vvr, Y'_vvv.

**Таблица 3.2. Отношение установившегося r' модели Mariner к линейному K'·δ**

| δ, ° | 0,02 | 0,1 | 0,5 | 2 |
|---|---|---|---|---|
| r'/(K'·δ) | 0,9999 | 0,998 | 0,950 | 0,689 |

Отсюда следует, что модель тренажёра с постоянным K' (линейный Номото) не может одновременно воспроизвести малые и большие перекладки (п. 3.5).

**3.2.3. Асимметрия винта.** Постоянные члены Y'₀, N'₀ (влияние винта) поворачивают судно на прямом руле со скоростью около 0,17 °/с при 15 уз. Тактический диаметр при руле 35° — 6,40L на ПБ и 6,65L на ЛБ.

Модель тренажёра симметрична, поэтому для идентификации эти члены выключены: тактический диаметр без них — 6,52L. Асимметрия — ограничение модели тренажёра (п. 3.8).

### 3.3. Расширения модели тренажёра

Добавлены в `ShipDynamicsModel` с переключателями в `ShipParameters`. По умолчанию выключены: `yawModel = Nomoto`, α' = 0, C_r' = 0.
- Прежние ассеты (`Default`, `Model45m`), сцена и тест эквивалентности A3.1 (`Refactor_MatchesLegacyStep_BitForBit`) не изменились — результат совпадает бит в бит.
- При α' = 0 ветка Норрбина тоже совпадает с Номото бит в бит (тест).

**Модель Норрбина** [15] вместо линейного Номото:

    T·ṙ + r + α·r³ = K·δ,   K = K'·u/L,   T = T'·L/U,   α = α'·(L/U)²,

в безразмерной форме T'·dr'/dt' + r' + α'·r'³ = K'·δ.
- α' ≥ 0 — модель устойчивого на курсе судна.
- Установившаяся циркуляция — корень r' + α'·r'³ = K'·δ, поэтому r' растёт с δ медленнее линейного (рис. `steady_turn_rate.svg`).

Интегрирование — экспонента с «замороженным» множителем g = 1 + α·r̄², где r̄ — середина шага (предиктор-корректор):

    r(t+dt) = K·δ/g + (r − K·δ/g)·e^(−g·dt/T).

- Схема устойчива при любом шаге.
- В установившемся режиме даёт точный корень кубического уравнения.
- Сходимость по шагу: при руле 35° и α' = 50 изменение курса за 300 с при dt = 0,02 с и dt = 0,002 с различается менее чем на 0,05° (тест).

**Потеря скорости на циркуляции:**

    du/dt = (u_зад − u)/τ − C_r'·L·r².

Обоснование формы. В уравнении продольной силы модели Абковица потерю скорости на повороте дают члены X'_vv·v'², X'_rr·r'², X'_vr·v'·r'. На циркуляции v' ∝ r', поэтому все три пропорциональны r'². В размерном виде ΔX/m = (X'/m')·L·r², откуда безразмерный коэффициент C_r'.
- Шаг точный при r = const: u(t+dt) = u* + (u − u*)·e^(−dt/τ), u* = u_зад − sign(u)·C_r'·L·r²·τ.
- Установившаяся потеря: Δu = τ·C_r'·L·r² (проверено тестом с точностью 10⁻⁶ м/с).
- Потеря только уменьшает |u| и не разворачивает ход.

В ходе тестирования найдена и исправлена ошибка. Первая версия ограничения «не разворачивать ход» обнуляла цель и при экстренном торможении (u_зад < 0 < u), и время остановки выросло в 5,4 раза. Исправленное условие срабатывает, только когда знак меняет сама потеря скорости. Тест `SpeedLoss_WithoutTurn_CrashStopUnchanged` подтверждает: без поворота торможение совпадает с исходным бит в бит.

### 3.4. Методика идентификации

Метод выходной ошибки (output error). Манёвр моделируется с кандидатными параметрами, и минимизируется среднеквадратичное расхождение с эталоном.
- Оптимизатор — симплекс Нелдера–Мида [12]: коэффициенты 1 / 2 / 0,5 / 0,5, один перезапуск из найденной точки.
- Поиск ведётся по логарифмам параметров, чтобы K', T', α' оставались > 0.
- Начальная точка — лучшая на грубой сетке K' ∈ {0,3…4,8}, T' ∈ {0,5…8}, α' ∈ {0,3…30}.
- Ручной подгонки нет: целевая функция и этапы зафиксированы в коде (`ShipCalibration`), результат воспроизводится тестом-регрессией.

**Повтор руля.** Модель тренажёра получает на каждом шаге тот же фактический угол руля δ(t), что эталон (рулевая машина без ограничения скорости на время идентификации). Подбираются параметры корпуса, а не различие рулевых машин. Эталонные манёвры записаны с шагом 0,02 с на 15 уз:
- циркуляции с рулём 10°, 20°, 35° — до поворота на 540°;
- зигзаги 10°/10° и 20°/20° — 5 перекладок.

**Последовательность.**
1. τ_u — аналитически: τ_u = m'₁₁·L/(−X'_u·U0) = **95,2 с** (линейная постоянная продольного движения при неизменных оборотах).
2. C_r' — по u(t) эталонных циркуляций при эталонном r(t) (одномерная минимизация): **C_r' = 0,806**.
3. K', T' (и α') — минимизация

       J = Σ_зигзаги (RMS Δψ / ψ_зад)² + Σ_циркуляции [(RMS r / |r_уст|)² + (RMS u / Δu_уст)²],

   где ψ_зад = 10° или 20°, r_уст и Δu_уст — установившиеся угловая скорость и потеря скорости эталона.

**Этапы** (одновременно — проверка, нужна ли нелинейная модель):
1. линейный Номото только по зигзагу 10°/10°;
2. линейный Номото только по циркуляции 35°;
3. линейный Номото по всем пяти манёврам;
4. Норрбин по всем пяти манёврам;
5. для сравнения — линеаризация Mariner без подбора (п. 3.2.2).

**Проверка метода на синтетических данных** (тест `Identification_RecoversKnownNorrbinParameters`). Эталон строится той же моделью Норрбина с K' = 2, T' = 3, α' = 10. Подбор восстанавливает их с погрешностью менее 1 % при J < 10⁻⁶.

**Анализ.**
1. **Линейный Номото не попадает одновременно в малые и большие перекладки.**
   - Подобранный по зигзагу 10°/10° (K' = 1,25) точно воспроизводит углы зарыскивания 10°/10° (0 и +6 %), но даёт тактический диаметр при 35° на 63 % меньше эталона.
   - Подобранный по циркуляции 35° (K' = 0,50) точно воспроизводит циркуляцию 35° (−1 %), но занижает углы зарыскивания 10°/10° на 82–86 % и завышает тактический диаметр при 10° на 136 %.
   - Компромисс по всем манёврам ошибается на 14–65 % почти во всех показателях.

   Причина — в эталоне эффективный коэффициент усиления r'/δ падает с ростом δ (табл. 3.2), а у линейной модели он постоянен. Это основание для перехода к модели Норрбина (требование плана: «если линейный Номото не даёт правдоподобных результатов одновременно на 10° и 35°»).
2. **Норрбин уменьшает J в 21 раз** (0,951 → 0,044). Отклонение от эталона: выдвиг и тактический диаметр — в пределах 5 % при всех углах руля; скорость на циркуляции — до 1 %; углы зарыскивания 20°/20° — до 5 %; времена поворота — до 12 %.
3. **Самопроверка.** K' = 3,48 и T' = 3,97, найденные у Норрбина, близки к аналитической линеаризации (K' = 3,86; T' = 5,14). Параметры получили физический смысл: K' — наклон кривой r'(δ) у нуля, а кубический член отвечает за насыщение на больших углах. У линейных моделей K', T' — эффективные значения, далёкие от физических (K' = 0,5…1,25).
4. **Остаточные расхождения Норрбина** структурны, а не результат недоподбора:
   - прямое смещение +16…+21 %: у модели 1-го порядка нет поперечной скорости v (угла дрейфа), траектория идёт по курсу;
   - начальная поворотливость +13 % и 1-й угол зарыскивания 10°/10° +29 % (4,12° → 5,30°, абсолютная разница 1,2°): в модели 1-го порядка нет числителя (1 + T'₃·s) — быстрой начальной реакции на руль. Кроме того, рулевые машины различаются (в эталоне апериодическое звено 1 с плюс ограничение 5 °/с, в тренажёре только ограничение).

### 3.8. Ограничения модели (выявлены калибровкой)

1. **Нет поперечной скорости (дрейфа):** прямое смещение на циркуляции +16…+37 %, траектория идёт по курсу.
2. **Модель поворота 1-го порядка:** нет T'₃ — быстрой начальной реакции; начальная поворотливость Mariner +13 %, время до 1-й перекладки у KCS −16…−26 %.
3. **Только устойчивые на курсе суда** (α' ≥ 0, линейный член +r): соотношение углов зарыскивания KCS не воспроизводится (2-й угол — до +37 %).
4. **Симметрия:** асимметрия от винта (у Mariner тактический диаметр 6,40L на ПБ против 6,65L на ЛБ) и уклонение при торможении не моделируются.
5. **Торможение, разгон, задний ход** — заглушки. У эталона Mariner постоянные обороты, натурный отчёт [4] недоступен, у KCS данных нет. Баланс тяги и сопротивления (план, п. 3) не вводился: его не по чему проверить.
6. **τ_разг Mariner** — постоянная продольного движения при n = const (95,2 с). Её использование для разгона с места — экстраполяция.
7. **Эталон Mariner — модель**, хотя и сопоставленная с натурой [3]. Прямое сравнение с натурными испытаниями [4] — после получения отчёта.
8. **Потеря скорости KCS** не калибровалась (C_r' = 0).

## 4. Качка судна на волнах (запрос 4)

### 4.1. Постановка

До запроса 4 качка была кинематической: крен, дифферент, рыскание и вертикальное смещение задавались суммой синусоид с амплитудой, пропорциональной интенсивности волнения I, и с волнами шейдера связаны не были (п. 0.4). Обучающийся видел, что судно качается «само по себе»: подъём на гребне не совпадал с волной у борта, характер качки не зависел от курса относительно волн и от хода.

**Цель:** судно качается на тех же волнах, которые видит обучающийся; длинные волны раскачивают судно, короткие — нет; частота встречи с волной зависит от курса и скорости.

**Что сделано:**
- математика поля волн вынесена в чистый класс `OceanWaveField` (сборка `VRBridge.Core`) — единый источник параметров для шейдера и C#;
- сэмплер высоты воды с обратной задачей Герстнера;
- модель качки `SeakeepingModel`: плоскость МНК по сетке точек корпуса и звенья 2-го порядка для вертикальной, бортовой и килевой качки;
- параметры мореходности в `ShipParameters` с оценкой периодов по формулам;
- режим `Waves` в `ShipMotion` (по умолчанию), синусоидальный режим сохранён как запасной;
- множитель комфорта и мягкие пределы крена и дифферента;
- стенд мореходности `Tools/VR Bridge/Seakeeping Trials` и 17 тестов.

### 4.2. Единый источник волн и единая шкала времени

Параметры четырёх волн Герстнера (направление D_i, волновое число k_i, крутизна (k·a)_i⁰, показатель n_i, множитель скорости c_i) хранятся в одном объекте `OceanWaveField`. Компонент сцены `OceanWaves` заполняет его из настроек инспектора и передаёт **те же значения float** в шейдер; сэмплер читает их же. Дублирования констант нет. Формула Герстнера записана дважды — в HLSL и C#; их совпадение проверяет тест `ShaderFormula_MatchesFieldFarFromOrigin` (судно в 20 км от начала мира, расхождение поверхностей < 2 мм).

Поле волны i в мировых координатах тренажёра (E — восток, N — север):

    f_i(P) = k_i·(D_i·P) − θ_i,     θ_i(t + Δt) = θ_i(t) + ω_i·c_i·s·Δt,     ω_i = √(g·k_i),
    a_i = (k·a)_i⁰ · I^{n_i} · F(ρ) · M_i(ρ) / k_i,

где s — множитель скорости волн от погоды, F — затухание с расстоянием ρ от судна (1,5…6 км), M_i — подавление волн мельче шага сетки (как в шейдере). Точка поверхности, «рождённая» в P₀:

    P = P₀ + Σ D_i·a_i·cos f_i(P₀),     z = Σ a_i·sin f_i(P₀).

**Время.** Раньше временные фазы θ_i накапливались в каждом кадре (`LateUpdate`, шаг кадра), а модель движения — в `FixedUpdate` с интерполяцией отображения. Для качки нужна одна шкала времени:
- θ_i продвигаются в `FixedUpdate` (симуляционное время, Δt = 0,02 с), там же модель качки читает воду;
- в кадре фазы для шейдера переносятся на время отображения навигации t_отобр = t_f − (1 − α)·Δt, α = (t − t_f)/Δt — по нему же `ShipNavigation` интерполирует курс и позицию, а `ShipMotion` — качку;
- θ линейна по времени, поэтому перенос точный (тест `RenderTimeOffset_IsExact`).

В результате вода, позиция судна и его качка в каждом кадре соответствуют одному моменту времени. Скорость волн на глаз не изменилась.

### 4.3. Высота воды в заданной точке

Волна Герстнера смещает точки поверхности по горизонтали, поэтому высоту в точке P нельзя получить подстановкой P в формулу z(P₀). Исходная точка P₀ находится итерациями

    P₀⁽⁰⁾ = P,     P₀⁽ᵐ⁺¹⁾ = P − Σ D_i·a_i·cos f_i(P₀⁽ᵐ⁾),

затем z = Σ a_i·sin f_i(P₀). Отображение сжимающее при Σ k_i·a_i < 1 (в шторм Σ k·a ≈ 0,55), погрешность убывает примерно в Σ k·a раз за итерацию. Фаза в самой точке P считается один раз в double по модулю 2π, в итерациях добавляется только малая поправка k·(D·(P₀ − P)) — точность не зависит от удаления от начала мира.

| Итераций | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| RMS ошибки высоты, м | 0,062 | 0,015 | 0,0041 | 0,0013 |

Принято 3 итерации: RMS 4 мм, максимум 3,7 см при размахе волн 5–7 м.

**Доступ для других объектов.** `OceanWaves.SampleHeight(WorldPosition)` и `OceanWaves.SampleWaterLevel(Vector3 сцены)` возвращают высоту воды в текущем кадре — для буёв (B1) и чужих судов (B3).

### 4.4. Возмущение: плоскость по точкам корпуса

Высота воды сэмплируется в n = n_x·n_y точках сетки по корпусу: n_x вдоль (от кормы до носа, ±L/2), n_y поперёк (±B/2), вокруг центра качки (мидель, диаметральная плоскость, ватерлиния). Точка j с координатами (x_j — к носу, y_j — к правому борту) в мире:

    P_j = P_c + x_j·(sin ψ, cos ψ) + y_j·(cos ψ, −sin ψ),

где P_c — центр качки, ψ — курс на шаге модели (из `ShipDynamicsModel`, с учётом плавающего начала координат). По точкам МНК строится плоскость z = h + s_x·x + s_y·y:

    [h, s_x, s_y]ᵀ = (AᵀA)⁻¹·Aᵀ·z,    A_j = [1, x_j, y_j].

Матрица (AᵀA)⁻¹Aᵀ зависит только от сетки и считается один раз. Волновое возмущение: ζ_w = h, θ_w = atan s_x (нос вверх), φ_w = −atan s_y (крен на правый борт).

**Размер сетки.** План предусматривал 4–6 точек. Принята сетка 5 × 3 = 15 точек: при 6 точках на корпусе длиной 45 м самая короткая волна (λ = 9 м) даёт наложение частот — ложное медленное покачивание. Сетка осредняет короткие волны по корпусу (для сплошного корпуса множитель ≈ sin(kL/2)/(kL/2)); дискретное осреднение грубее (п. 4.11). Стоимость 15 точек — около 3 мкс на шаг на ПК (п. 4.9). Сетка настраивается в инспекторе (2…9 × 2…5).

### 4.5. Динамика качки

Корпус — не поплавок: каждая степень свободы описывается звеном 2-го порядка с собственной частотой ω₀ = 2π/T₀ и относительным затуханием ζ₀:

    ẍ + 2ζ₀ω₀ẋ + ω₀²x = ω₀²·x_w,     x ∈ {ζ, φ, θ}.

- Статический коэффициент равен 1: на очень длинной волне судно лежит на её склоне (гидростатический предел).
- Амплитудно-частотная характеристика (АЧХ): |H| = 1/√((1 − Λ²)² + (2ζ₀Λ)²), Λ = ω_e/ω₀. Короткие (частые) волны гасятся, у резонанса (Λ ≈ 1) отклик усиливается в 1/(2ζ₀) раз.
- Возмущение по уклону волны соответствует гидростатической (Фруда–Крылова) части сил без дифракции и радиации; инерция и демпфирование корпуса заданы эквивалентно — через T₀ и ζ₀ [4.3, 4.4].

**Дискретизация** точная при постоянном на шаге входе (как в модели движения, п. 0.3):

    e = x − x̄_w,   [e; ẋ](t + Δt) = Φ·[e; ẋ](t),   Φ = exp(A·Δt),   A = [[0, 1], [−ω₀², −2ζ₀ω₀]],
    Φ = e^{−σΔt}·[[cos + (σ/ω_d)·sin,  sin/ω_d], [−(ω₀²/ω_d)·sin,  cos − (σ/ω_d)·sin]],
    σ = ζ₀ω₀,   ω_d = ω₀·√(1 − ζ₀²),   cos, sin — от ω_d·Δt.

Вход на шаге x̄_w = (x_w(t) + x_w(t + Δt))/2 — без запаздывания на полшага. Схема устойчива при любом Δt; ζ₀ ограничен 0…0,95. Проверка: свободные затухающие колебания совпадают с аналитическим решением с точностью 10⁻⁹ (тест `Oscillator_FreeDecay_MatchesAnalytic`), в резонансе усиление крена 5,00 = 1/(2·0,1) (тест `ResonantWave_RollAmplifiedBy1Over2Zeta`).

**Частота встречи.** Судно движется по полю волн, поэтому частота возмущения — частота встречи

    ω_e = ω − k·U·cos μ,

μ — угол между курсом и направлением распространения волны (0 — попутная, 180° — встречная). Она в модели не задаётся, а возникает сама; тест `EncounterPeriod_MatchesTheory` (одна волна λ = 90 м, 15 уз) даёт совпадение измеренного периода с теорией до 0,001 с:

| Курсовой угол волны q | 0° (встречная) | 60° | 180° (попутная) |
|---|---|---|---|
| T_e: теория / модель, с | 4,599 / 4,599 | 5,728 / 5,728 | 21,753 / 21,753 |

(собственный период волны 7,59 с).

**Отображение.** Состояние качки интерполируется между шагами физики с тем же α, что курс и позиция. Судно поворачивается вокруг центра качки, а не вокруг начала объекта `Ship`, которое лежит на 5 м выше воды и на 2,7 м в стороне от диаметральной плоскости. Рыскание от волн не моделируется — курсом управляет модель A2/A3.

### 4.7. Комфорт (укачивание)

Для экспериментов с ограничением качки введены (только для отображения, физику модели не меняют):
- общий множитель амплитуды k_комф ∈ [0; 1] на все три степени свободы;
- мягкие пределы крена и дифферента x_отобр = x_max·tanh(x/x_max): у нуля наклон 1 (малая качка не искажается), производная непрерывна — без рывков при подходе к пределу. По умолчанию φ_max = 20°, θ_max = 8°, k_комф = 1.

При k_комф < 1 судно поднимается на волне меньше, чем вода у борта, — это осознанный компромисс режима эксперимента.

Это известный опасный режим (попутное волнение с кормовых курсовых углов), который модель воспроизводит без специальной настройки. Для тренажёра это учебная ситуация: изменение курса или скорости выводит судно из резонанса.
4. **Множитель скорости волн погоды.** В шторм волны быстрее физической дисперсии в s = 1,3 раза (`speedInfluence` = 0,25 при `_WaveSpeed` = 2,2 — решение этапа A1), поэтому период волны 1 — 5,84 с вместо 7,59 с, и на стопе резонанса нет. Теоретический T_e в стенде учитывает s.
5. **Короткие волны не раскачивают судно.** Волна λ = 9 м даёт вертикальную качку 0,3…13 % её амплитуды и крен ≤ 0,12° (тест `ShortWave_IsFilteredOut`); рябь (λ ≤ 4,1 м) в высоту воды не входит вовсе.
6. **Штиль**: максимум крена 1,1°, дифферента 0,4°, вертикальной качки 0,14 м (тест `Calm_AlmostNoMotion`).

### 4.9. Производительность

Шаг модели качки (15 точек × 3 итерации × 4 волны, МНК, три звена) на ПК — 4,7 мкс в редакторе Unity (среднее по 52 случаям стенда) и около 3 мкс в сборке Release вне Unity. В `FixedUpdate` (50 Гц) это ≈ 0,15 мс в секунду, то есть доли процента бюджета кадра 11,1 мс. На автономном Quest 3 (ARM) время в несколько раз больше, но остаётся в десятках микросекунд; при необходимости сетку можно уменьшить в инспекторе.

### 4.11. Ограничения модели

1. **Гидростатическое возмущение.** Сила от волны берётся по уклону поверхности под корпусом (часть Фруда–Крылова). Дифракция, радиация и эффект Смита (уменьшение давления с глубиной: при осадке 3 м и λ = 20 м множитель e^{−kd} ≈ 0,4) не учитываются, поэтому короткие волны раскачивают судно несколько сильнее, чем в действительности.
2. **Затухание линейное.** У бортовой качки реальное демпфирование нелинейное (квадратичное по скорости, вязкое и от боковых килей), в резонансе оно ограничивает амплитуду сильнее. Модель с ζ_φ = 0,1 даёт крен до 27° в резонансе — для отображения действует мягкий предел 20°.
3. **Независимые степени свободы.** Связи вертикальной и килевой качки, крена с рысканием и креновый момент на циркуляции не моделируются; рыскание и горизонтальные смещения от орбитального движения частиц воды — тоже.
4. **Дискретная сетка точек.** 3 точки поперёк корпуса шириной 8,6 м осредняют волну λ = 9 м лагом грубее сплошного корпуса (13 % против ≈ 5 %); в абсолютных величинах это сантиметры.
5. **Параметры судна сцены — допущения**: GM, C_B, C_WP и затухания не взяты из документации (у мостика 45 м нет прототипа с формуляром).
6. **Корпус у борта.** Шейдер гасит волны в полосе 8 м у корпуса до 25 % (A1.1). При вертикальной качке до ±2 м в шторм вода у борта может визуально расходиться с корпусом. Решение (вода у борта стремится к плоскости ватерлинии судна, а не к нулю) — отдельная правка шейдера после проверки в шлеме.
7. **Множитель скорости волн погоды** (s до 1,3 в шторм) нарушает дисперсию глубокой воды. Качка и частота встречи считаются с тем же s, что и видимые волны, — согласованность сохранена.

## 5. Учебная акватория и посадка на мель (запрос 5, B1)

### 5.1. Постановка

До запроса 5 судно шло по пустой воде: в районе плавания не было ни навигационного ограждения, ни опасностей. Сценарии с проходом фарватером и оценку действий обучающегося (B2, C2) строить было не на чем.

**Цель:** синтетическая учебная акватория в локальной системе координат тренажёра (восток/север в метрах от условного начала), в которой есть:
- знаки навигационного ограждения МАМС;
- мели и суша;
- контроль глубины под судном и модель посадки на мель.

Реальные карты (S-57, OpenSeaMap) сознательно не используются. Учебной задаче нужна управляемая и воспроизводимая обстановка, которую преподаватель может изменить без картографических инструментов и лицензий.

**Что сделано:**
- модель данных акватории (`WaterArea`, сборка `VRBridge.Core`): знаки, мели, суша, фарватеры, границы района;
- процедурные low-poly модели знаков МАМС (регион A) с окраской и топовыми фигурами; знаки качаются на волнах через сэмплер запроса 4;
- редактирование акватории мышью в Scene View;
- детектор опасного приближения и посадки на мель (`GroundingDetector`) по контуру корпуса;
- режим «на мели» в модели движения: наползание, остановка, съём задним ходом;
- сигнализация глубины на мостике, звук удара и скрежета, тряска камеры;
- вызываемое VR-меню команд мостика (кнопка A);
- демонстрационная акватория для первого сценария;
- 18 автоматических тестов.

### 5.4. Отображение и качание на волнах

**Неподвижность в мире.** Позиция знака в сцене каждый кадр вычисляется в double: p_сцены = p_мира − p_судна (`WorldOrigin.WorldToScene`). Поэтому знаки стоят на месте, когда судно идёт, а точность не зависит от удаления от начала мира.

Суша и отладочные линии строятся в координатах относительно центра района, смещается только их корневой объект. Погрешность float на расстоянии 6 км ≈ 0,5 мм.

**Качание.** Высота знака равна высоте воды в его точке в текущем кадре: `OceanWaves.SampleHeight`, обратная задача Герстнера (п. 4.3). Это те же волны и тот же момент времени отображения, которые видит обучающийся и по которым качается своё судно.

Наклон знака задаётся уклоном воды по двум дополнительным точкам на расстоянии r:

    s_E = (h(E + r, N) − h(E, N)) / r,    s_N = (h(E, N + r) − h(E, N)) / r,
    n = norm(−k·s_E, 1, −k·s_N).

Параметры:
- k — доля следования уклону, 0,8: буй частично «стоит» за счёт остойчивости;
- r = 1,5 м;
- вертикаль буя n сглаживается с постоянной τ = 0,3 с (инерция буя);
- высота не сглаживается, чтобы буй не «тонул» в гребне.

Собственная динамика буя (периоды, затухание) сознательно не моделируется: на дистанциях, с которых знак виден с мостика, разница неразличима.

**Видимость.** Первая проверка в шлеме показала, что знаки со старта не видны: туман пресетов погоды (этап A1, ExponentialSquared, f = exp(−(ρ·d)²)) давал дальность видимости d = √(−ln 0,05)/ρ ≈ 1,73/ρ всего 1,7 км в штиль, 0,6 км в умеренное волнение и 70 м в шторм. Такая видимость соответствует туману, а не обычной погоде, и для навигационного упражнения непригодна. Плотности пересчитаны под морскую видимость:

| Пресет | ρ было | d было | ρ стало | d стало |
|---|---|---|---|---|
| Штиль | 0,001 | 1,7 км | 0,0003 | 5,8 км |
| Умеренное | 0,003 | 0,58 км | 0,0004 | 4,3 км (2,3 мили) |
| Шторм | 0,025 | 69 м | 0,0015 | 1,2 км |
| Ночь | 0,008 | 0,22 км | 0,0004 | 4,3 км |

Первый вариант (10 / 6,9 / 1,4 / 5,8 км) открывал край меша океана (10 км, f ≈ 0,06 в штиль) — в шлеме был виден «конец горизонта». Принятые значения скрывают край (в штиль f = e^(−9) ≈ 10⁻⁴) и оставляют видимыми знаки фарватера на 2–4 км. По той же проверке ослаблена рябь (детальные волны в нормалях): detailStrength 0,6 → 0,12 (промежуточное 0,35 давало заметный «плиточный» узор из 4 детальных волн). Видимость как условие сценария и её связь с плотностью тумана — запрос C4.

**Производительность.**
- На знак — 3 вызова сэмплера, ≈ 0,3 мкс каждый.
- Знаки дальше 3,5 км обновляют высоту раз в 10 кадров, позицию — каждый кадр. Волны там всё равно гаснут (затухание 1,5…6 км, п. 0.4).

### 5.5. Контроль глубины и посадки на мель

**Контур корпуса** — прямоугольник L × B, повёрнутый по курсу ψ:

    C = P + x_c·f + y_c·s,    f = (sin ψ, cos ψ),    s = (cos ψ, −sin ψ),
    углы: C ± (L/2)·f ± (B/2)·s,

где:
- P — позиция судна (точка ShipRoot);
- f — направление к носу, s — к правому борту;
- (x_c, y_c) — смещение середины корпуса: центр качки ShipMotion (мидель, диаметральная плоскость).

**Опасные объекты.** Мель опасна для судна, если её наименьшая глубина

    h < d + Δ,

где d — осадка (из `ShipParameters`), Δ — запас под килем. Суша опасна всегда. Поэтому одна и та же банка опасна для глубокосидящего судна и безопасна для мелкосидящего (банка 6 м в демонстрационной акватории).

**Расстояние** D от контура корпуса до многоугольника:
- D = 0, если рёбра пересекаются или один многоугольник целиком лежит внутри другого;
- иначе D — минимум расстояний между рёбрами. Для непересекающихся отрезков минимум достигается на конце одного из них.

Пересечение отрезков проверяется по знакам ориентаций o(a, b, c) = (b − a) × (c − a). Перед точным расчётом многоугольники отсеиваются по охватывающим прямоугольникам. D_min берётся по всем опасным объектам.

**Состояния и переходы:**

    Чисто → Опасное приближение,   если D_min < D_пред;
    Опасное приближение → Чисто,   если D_min > D_пред·(1 + η);
    любое → На мели,               если D_min = 0;
    На мели → Приближение / Чисто, если пересечения больше нет (судно снялось).

**Свойства проверки:**
- Гистерезис η исключает «дребезг» сигнализации, когда судно идёт вдоль границы D_пред (тест `Warning_Hysteresis_NoChatter`).
- Проверка выполняется на каждом шаге модели (50 Гц). При 15 уз судно проходит за шаг 0,15 м, поэтому «проскочить» даже узкую мель нельзя.
- Стоимость проверки — 3,3 мкс на шаг на ПК (демонстрационная акватория: 5 мелей и 2 участка суши).

**Таблица 5.3. Параметры контроля глубины**

| Параметр | Обозначение | Значение | Примечание |
|---|---|---|---|
| Осадка | d | 3,0 м | `ShipParameters_Model45m` |
| Запас под килем | Δ | 0,5 м | предварительное значение, параметр |
| Дистанция опасного приближения | D_пред | 185,2 м (1 кбт) | предварительное значение, параметр |
| Гистерезис выхода | η | 0,1 | |
| Постоянная остановки на грунте | τ_ост | 1,0 с | |
| Доля скорости при съёме | k_снят | 0,3 | |

Значения Δ и D_пред предварительные:
- нормативный запас под килем зависит от района, осадки, скорости и волнения и обычно задаётся местными правилами плавания;
- дистанция срабатывания сигнализации задаётся настройкой навигационной аппаратуры.

Обоснование конкретных значений для упражнений — в главе 2 ВКР.

### 5.6. Динамика судна на мели

Режим «на мели» добавлен в `ShipDynamicsModel` (п. 2.1). При выключенном режиме шаг модели не изменился: существующие тесты проходят бит в бит. В момент касания запоминается направление хода s = sign(u).

1. **Наползание.** Ход в сторону мели гаснет независимо от работы машины:

        u(t + Δt) = u(t)·e^(−Δt/τ_ост)   при u·s > 0.

   Путь наползания (дискретно, Эйлер по позиции):

        Δx = u₀·Δt·q / (1 − q),   q = e^(−Δt/τ_ост),   Δx ≈ u₀·(τ_ост − Δt/2).

   Судно «вылезает» на грунт тем дальше, чем больше скорость, и останавливается за ≈ 3·τ_ост.
2. **Работа машиной «в мель»** судно не двигает (u_цель = 0), но сопровождается скрежетом и тряской (п. 5.7).
3. **Съём.** Ход от мели (−s) разрешён, но с повышенным сопротивлением грунта:

        u_цель = k_снят·u_зад   (если u_зад·s < 0, иначе 0),
        u(t + Δt) = u_цель + (u − u_цель)·e^(−Δt/τ_разг).

   Судно снимается, когда контур корпуса перестаёт пересекать опасный объект. Это решает детектор (п. 5.5).
4. **Поворот на мели:** r(t + Δt) = r·e^(−Δt/τ_ост). Корпус лежит на грунте, руль не действует, хотя рулевая машина руль перекладывает.

**Посадка кормой.** На заднем ходу судно может сесть кормой; тогда оно снимается передним ходом (тест `GroundedOnSternway_AheadRefloats`).

**Снятие инструктором** (команда меню):
- судно переставляется на последнюю «чистую» позицию примерно за 30 с до посадки;
- курс прежний, судно на стопе;
- телеграф переводится на «Стоп».

**Таблица 5.4. Посадка на мель** (судно сцены, L = 45 м, курсом на мель глубиной 2 м; после остановки — «полный назад»)

### 5.7. Сигнализация, звук, тряска, меню мостика

**Сигнализация глубины на мостике** работает как сигнализация эхолота или навигационного планшета. Это полоса над панелью навигации:
- в обычном режиме — глубина по карте под серединой корпуса и запас под килем;
- при опасном приближении — мигающая надпись «ОПАСНО: МЕЛЬ x кбт» с названием и глубиной мели, двойной тон 1200 Гц раз в 3 с;
- на мели — постоянная надпись «НА МЕЛИ», тройной тон 880 Гц раз в 2 с.

Квитирование (команда меню) глушит звук. Надпись остаётся, пока опасность не миновала. Новое опасное событие снимает квитирование.

**Звук посадки:**
- удар — низкочастотный удар 38/57 Гц, шум грунта, скрип набора;
- скрежет — полосовой шум 140…750 Гц с рывками «прилипание — срыв», петля 3 с.

Громкость и высота скрежета растут с уровнем скрежета

    L = clamp(max(√(|u|/V_эксп), 0,35·|SF|·[SF·s > 0]), 0, 1).

Скрежет звучит, пока судно ползёт по грунту, а также при работе машиной «в мель». Звуки — процедурные заглушки; свои записи назначаются в инспекторе.

**Тряска камеры.** По решению пользователя трясётся не корпус, а камера: смещается и поворачивается объект «Camera Offset» XR-рига (родитель камеры и контроллеров). Трекинг шлема при этом не затрагивается.
- Удар — импульс до 3 см и 0,6°, гаснущий с постоянной 0,35 с.
- Скрежет — до 1,2 см и 0,25°, пропорционально L.
- Шум Перлина ≈ 11 Гц.
- Амплитуды малы и умножаются на коэффициент комфорта — против укачивания в VR.

**Меню мостика.** Пользователь попросил управлять тренажёром без клавиатуры, поэтому введено вызываемое VR-меню на кнопке A правого контроллера.
- Прыжок шаблона XR занимал эту кнопку и отключён: на мостике он не нужен.
- Панель появляется перед обучающимся и закреплена в системе судна.
- Меню не знает конкретных команд. Модули регистрируют их сами: группа, название, условие доступности, действие. Поэтому новые функции (перезапуск сценария B2, погода, вводные инструктора D1) добавляются без правки меню.
- Команды B1: «Снять с мели» (инструктор), «Квитировать сигнализацию», «Показать/скрыть мели на воде» (отладка).

### 5.11. Ограничения модели

1. **Глубина постоянна в пределах мели** (наименьшая глубина многоугольника). Нет рельефа дна, изобат, приливов. Для упражнений на ограждение этого достаточно; для упражнений на запас под килем нужен рельеф.
2. **Нет влияния мелководья на судно.** Не моделируются проседание (squat), рост сопротивления и ухудшение поворотливости на малой глубине, присасывание к бровке канала.
3. **Контур корпуса — прямоугольник** L × B, без скругления носа и кормы. Осадка постоянна: без дифферента, крена и вертикальной качки. Посадка «срабатывает» на 0…2 м раньше, чем у реального обвода в оконечностях.
4. **Модель посадки феноменологическая.** Экспоненциальная остановка с τ_ост и сопротивление съёму k_снят не выведены из сил трения о грунт, нагрузки на грунт и деформации корпуса; повреждения не оцениваются. Для тренажёра важны факт посадки и правильные действия при съёме, а не точная механика.
5. **Качка на мели продолжается:** судно «на волнах» над грунтом. Это визуальное допущение.
6. **Мели на воде не видны**, как в действительности: нет изменения цвета воды, бурунов над камнем, обрушения волн на отмели.
7. **Буи** не имеют собственной динамики (следуют уровню и уклону воды) и огней (огни — B4). Столкновение судна с буем не моделируется.
8. **Сигнализация упрощённая:** она работает по карте района, а не по эхолоту, и «видит» мель заранее по контуру — как навигационный планшет с контролем безопасной глубины.

## 6. Движок сценариев (запрос 6, B2)

### 6.1. Постановка

После запроса 5 у тренажёра была учебная акватория, но не было упражнения как такового. Не было задачи и брифинга, единых начальных условий, маршрута с допусками, условий завершения и записи того, что произошло во время упражнения. Всё это — предпосылки сценарной оценки действий обучающегося (C2), ради которой строится модуль.

**Цели:**
- сценарий создаётся без программирования — заполнением ассета (ScriptableObject);
- жизненный цикл упражнения: выбор → брифинг → выполнение → завершение (с причиной) → результаты;
- шина событий упражнения: модули (контроль маршрута, контроль глубины, будущие запись, оценка, тактильный отклик) не ссылаются друг на друга;
- контроль движения по маршруту: прохождение путевых точек, выход за допустимый коридор и возврат;
- первый сценарий на демонстрационной акватории.

**Решение пользователя (с B1): без клавиатуры.** Выбор сценария, брифинг, «Начать», перезапуск и досрочное завершение — через VR-меню мостика (кнопка A) и VR-панель. Клавиатура и мышь инструктора появятся только в окне инструктора (D1).

Как и в предыдущих разделах, расчётная часть — в чистых классах сборки `VRBridge.Core`. Их можно проверять автоматическими тестами без сцены и использовать офлайн, по записанной сессии (C1, C2). Сцена содержит тонкие компоненты Unity.

| Оценка | ссылка на `AssessmentCriteria` | заготовка для C2 |

**Начальные условия.** Скорость в начальных условиях и положение телеграфа задаются независимо, как на реальном судне в момент «приёма вахты». Если начальная скорость отличается от установившейся при этом положении телеграфа, судно разгоняется или тормозит по модели п. 0.3. Инспектор сценария показывает установившуюся скорость: u_уст = SF·V_эксп (вперёд), SF·V_эксп·k_зх (назад).

**Проверка описания.** Метод `Validate()` и инспектор ассета показывают проблемы сценария:
- меньше двух путевых точек, XTE_доп ≤ 0, совпадающие точки;
- точки или старт вне района, старт на мели;
- пустой брифинг, не назначена акватория;
- включено условие «истечение времени» при нулевом лимите.

### 6.4. Жизненный цикл упражнения

    Свободное плавание ─(выбор)→ Брифинг ─(«Начать»)→ Выполнение ─(причина)→ Результаты
          ↑                         │  ↑                    │                     │
          └──(свободное плавание)───┘  └──── перезапуск ─────┴─────────────────────┘

1. **Загрузка (брифинг).**
   - применяются параметры судна, акватория и погода — погода сразу, без 3-секундного перехода пресетов;
   - судно ставится в начальную точку: позиция, курс, скорость, фактический руль (`ShipNavigation.TeleportTo`), сброс контроля глубины (`GroundingMonitor.ResetState`), телеграф и штурвал;
   - **модель движения стоит** (`ShipNavigation.Paused`): пока обучающийся читает брифинг, судно с начальной скоростью 15 уз не уходит из точки старта;
   - качка продолжается, кильватерный след на паузе не рисуется.
2. **«Начать».**
   - начальные условия ставятся повторно: если на брифинге трогали штурвал или телеграф, упражнение всё равно начинается из заданного состояния;
   - пауза снимается, журнал шины очищается, время упражнения обнуляется, публикуется «начало».
3. **Выполнение.** На каждом шаге модели (50 Гц):
   - t_упр += Δt;
   - контроль маршрута (п. 6.5) → события шины;
   - проверка лимита времени.

   Порядок выполнения −88 — после шага модели (−90) и до контроля глубины (−85). Поэтому события маршрута и мели одного шага получают одно и то же время упражнения.
4. **Завершение.** Причины:
   - прибытие в последнюю точку;
   - посадка на мель;
   - столкновение (с B3);
   - истечение времени;
   - досрочное завершение инструктором.

   Публикуется «конец» с причиной, журнал сохраняется, строится предварительный итог, судно переходит в свободное плавание. Если условие «посадка» в сценарии выключено, посадка — только событие: можно отрабатывать съём с мели (п. 5.6).

**Время упражнения** — симуляционное: сумма шагов модели от «Начать». Брифинг в него не входит.

### 6.5. Контроль движения по маршруту

Маршрут — ломаная путевых точек W₀…W_n. Участок i ведёт от W_i к W_{i+1}. Точка отсчёта — позиция судна в модели (ShipRoot).

**Боковое отклонение и пройденный путь по участку:**

    t = (W_{i+1} − W_i) / |W_{i+1} − W_i|      — направление участка,
    n = (t_N, −t_E)                            — нормаль вправо от линии пути,
    XTE = (P − W_i)·n                          — боковое отклонение, м (> 0 — правее линии пути),
    ATD = (P − W_i)·t                          — пройдено вдоль участка, м.

**Прохождение точки.** Точка W_{i+1} считается пройденной, когда судно пересекает линию прохождения:
- во **внутренней** точке — биссектрису угла поворота: (P − W_{i+1})·(t + t₂) ≥ 0, где t₂ — направление следующего участка. На прямой (t₂ = t) это перпендикуляр к участку; при развороте на 180° (t + t₂ = 0) берётся перпендикуляр;
- в **последней** точке — перпендикуляр к участку (линию финиша): ATD ≥ |W_{i+1} − W_i|.

Свойства правила:
- Точки проходятся строго по порядку; за один шаг может пройти несколько (после перестановки судна).
- В момент прохождения фиксируется XTE по входящему участку.
- Биссектриса, а не «круг прибытия» радиуса R, выбрана потому, что не зависит от параметра R. Точку нельзя «не задеть», пройдя мимо круга: факт прохождения и точность (XTE) разделены.

**Коридор.** Для участка i допустимое отклонение XTE_доп задаётся у точки W_{i+1}:

    выход:   |XTE| > XTE_доп;
    возврат: |XTE| < XTE_доп·(1 − η),   η = 0,05.

Гистерезис η исключает «дребезг» событий, когда судно идёт вдоль границы коридора (тест `Corridor_ExitAndReturn_WithHysteresis_NoChatter`) — так же, как у сигнализации мели (п. 5.5). При выходе запоминаются время и наибольшее |XTE|. При возврате публикуются наибольшее отклонение и длительность выхода.

После прохождения точки XTE считается по новому участку, и состояние коридора пересчитывается по новому XTE_доп. После прибытия в последнюю точку контроль прекращается.

**Статистика упражнения** (для итога, в C2 — для критериев маршрута):
- наибольшее |XTE|;
- суммарное время вне коридора;
- число выходов;
- число пройденных точек.

### 6.6. Шина событий упражнения

Шина `ExerciseEvents` — статический класс (как реестр команд меню, п. 5.7). События рассылаются синхронно, в том же шаге. Ошибка одного подписчика не мешает остальным. Событие, опубликованное подписчиком во время рассылки (на «посадку» — «конец упражнения»), ставится в очередь и доставляется после текущего: порядок «причина → следствие» одинаков у всех подписчиков.

**Время события ставит шина** — время упражнения, которое ведёт `ScenarioRunner`. У всех источников одни часы. События вне упражнения (свободное плавание) рассылаются, но в журнал упражнения не попадают.

Одна запись на все типы событий: тип, время, признак «в упражнении», позиция, курс, скорость, номер, два числовых значения, название объекта, причина завершения, признак «инструктор». Такая запись — готовая строка будущего `events.csv` (C1).

### 6.11. Ограничения

1. **XTE считается по точке ShipRoot**, без учёта положения антенны и габаритов корпуса. Габариты учтены запасом в XTE_доп. Касание кромки фарватера корпусом отдельно не контролируется — его заменяет контроль мелей (п. 5.5).
2. **Прохождение точки не зависит от отклонения.** Точка засчитывается при пересечении линии прохождения даже далеко от неё. Точность контролируется отдельно — коридором и XTE в момент прохождения. Если судно не пересекло линию прохождения (ушло в сторону и вернулось на другой участок), точка не засчитывается, а следующие ждут её.
3. **Пауза** есть только на брифинге. Пауза во время упражнения (инструктор) — D1.
4. **Время суток и видимость** — только поля сценария. Ночь пока задаётся пресетом погоды «Ночь» (B4), видимость — плотностью тумана пресета (C4).
5. **Другие суда и столкновение** — заготовка данных и событие шины (B3). **Критерии оценки** — заготовка ассета (C2). **Результаты** — предварительный итог без оценки (C3).
6. **Шина синхронная, одна на сцену.** Одновременно выполняется одно упражнение. Запись в файл (C1) должна буферизоваться, чтобы не задерживать шаг модели.
7. **Допуски** XTE_доп (250/150 м), лимит времени (30 мин) и упреждение авторулевого тестов (150 м) — предварительные значения, их обоснование — в главе 2.

**Исправлено по итогам проверки — порядок доставки событий.** В первой версии шины ScenarioRunner, получив «посадку», публиковал «конец упражнения» прямо внутри рассылки. Подписчики, стоящие после него (консоль, в будущем — запись C1), получали «конец» раньше «посадки». Журнал упражнения при этом был упорядочен верно.

Теперь событие, опубликованное во время рассылки, ставится в очередь и доставляется после текущего. Порядок «причина → следствие» одинаков у всех подписчиков и в журнале, время у обоих событий одно. Тест — `Bus_NestedPublish_DeliveredAfterCurrentEvent`.
