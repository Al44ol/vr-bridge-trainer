### 0.2. Плавающее начало координат (A1)

**Проблема.** Одинарная точность float (24 бита мантиссы) на удалении 10 км даёт шаг представления около 1 мм, а на 100 км — около 8 мм. Это вызывает дрожание геометрии и камеры в VR, где заметны даже миллиметровые рывки.

**Решение.** Судно и наблюдатель всегда находятся около начала координат сцены. Истинная позиция судна хранится в двойной точности: `WorldPosition {double East, North}`, метры. Объекты мира ставятся в сцену через преобразование `p_сцены = p_мира − p_судна`. Система координат: +X — восток, +Z — север.

**Вода.** Фазы волн считаются на CPU в double как `φ = k·(d·p_судна) − ω·t (mod 2π)` и передаются в шейдер, поэтому смещение мира не накапливает погрешность.

### 0.3. Модель движения судна (A2)

Обозначения: ψ — курс (0 = N, по часовой); r — угловая скорость; u — скорость хода; δ — перекладка руля (> 0 — правый борт); L — длина судна; SF — положение телеграфа (−1…1).

1. **Рулевая машина.** dδ/dt = clamp((δ_зад − δ)/dt, −ω_δ, +ω_δ), |δ| ≤ δ_max. По СОЛАС гл. II-1, правило 29, перекладка с 35° одного борта на 30° другого занимает не более 28 с, поэтому ω_δ = 65°/28 с ≈ 2,32 °/с.
2. **Скорость.** du/dt = (u_зад − u)/τ.
   - u_зад = SF·V_эксп при SF ≥ 0 и SF·V_эксп·k_зх при SF < 0.
   - τ = τ_разг при разгоне и τ_торм при торможении.
   - Дискретизация точная: u(t+Δt) = u_зад + (u − u_зад)·e^(−Δt/τ).
3. **Поворот — модель Номото 1-го порядка.** T·ṙ + r = K·δ, где K = K'·U/L и T = T'·L/U.
   - Точная дискретизация: r(t+Δt) = Kδ + (r − Kδ)·e^(−Δt/T).
   - Диаметр установившейся циркуляции D = 2L/(K'·δ) не зависит от скорости.
4. **Кинематика** (в double): ψ += r·Δt, E += u·sin ψ·Δt, N += u·cos ψ·Δt.
5. **Шаг интегрирования.** FixedUpdate, Δt = 0,02 с (50 Гц). Отображение интерполируется к 90 Гц: α = (t − t_fixed)/Δt.

### 0.4. Морская поверхность (A1)

- **Геометрия.** Радиальный меш радиусом 10 км, около 98 тыс. вершин, со сгущением к центру.
- **Крупные волны.** Четыре волны Герстнера (λ = 90/45/20/9 м) веером вокруг направления ветра. Амплитуда a_i = a_i⁰·I^{n_i}, где I — интенсивность волнения пресета погоды. Дисперсия глубокой воды: ω = √(g·k).
- **Рябь.** Ещё четыре мелкие волны (λ = 4,1…0,75 м) только в нормалях, без смещения вершин.
- **Затухание.** Волны гаснут на 1,5…6 км; волны мельче шага сетки или размера пикселя подавляются, чтобы не было алиасинга.
- **Пена.** Барашки — по крутизне гребня Σ k·a·sin φ. За кормой — кильватерный след с углом Кельвина 19,47°.
- **Качка.** Пока кинематическая — сумма синусоид, с волнами не связана (запрос 4).

## 1. Технический долг: Single Pass Instanced, дождь, правила журнала (запрос 1)

### 1.1. Переход OpenXR с Multi-pass на Single Pass Instanced

**Что сделано.** Режим стереорендеринга для PC (Standalone) переключён с Multi-pass на Single Pass Instanced (SPI) через новый пункт меню `Tools/VR Bridge/OpenXR Render Mode`. Пункт оставлен двусторонним: оба режима можно сравнить на одной сцене.

**Обоснование.**
- **Multi-pass.** Сцена проходится дважды, по разу на каждый глаз: удваиваются отсечение, сортировка, отправка вызовов отрисовки (draw calls) и смена состояний на CPU.
- **SPI.** Каждый объект рисуется один раз с инстансингом ×2 в текстурный массив из двух слоёв. Номер глаза (`unity_StereoEyeIndex`) выбирается по `SV_InstanceID`, вершинный шейдер берёт свою матрицу вида-проекции для каждого глаза.
- **Ожидаемый эффект.** Число вызовов отрисовки и SetPass-вызовов уменьшается примерно вдвое. Для GPU выигрыш меньше: растеризуется столько же пикселей, но меньше переключений состояния и повторной обработки геометрии.

**Тонкость Play Mode.** Тренажёр проверяется в Play Mode через Virtual Desktop, а активная платформа проекта — Android. При этом OpenXR в Play Mode берёт настройки Standalone (`OpenXRSettings.GetInstance`: в редакторе — `BuildTargetGroup.Standalone`). Поэтому переключался именно режим Standalone; для Android SPI был включён и раньше.

**Проверка шейдеров.**

| Шейдер | Назначение | Поддержка SPI | Изменения |
|---|---|---|---|
| `VRBridgeTrainer/OceanSurface` | вода | полная¹ | не потребовались |
| `VRBridgeTrainer/SkyboxHorizonFog` | небо | полная² | не потребовались |
| URP Lit, URP Particles/Unlit | судно, мостик, дождь | встроенная | — |
| TextMesh Pro, шейдеры XRI/VR Template | интерфейс, руки | встроенная | не трогаем |

¹ В шейдере воды есть `#pragma multi_compile_instancing`, `UNITY_VERTEX_INPUT_INSTANCE_ID` во входной и выходной структурах, `UNITY_VERTEX_OUTPUT_STEREO`, `UNITY_SETUP_INSTANCE_ID` / `UNITY_TRANSFER_INSTANCE_ID` / `UNITY_INITIALIZE_VERTEX_OUTPUT_STEREO` в вершинной программе и `UNITY_SETUP_STEREO_EYE_INDEX_POST_VERTEX` во фрагментной. Положение камеры берётся через `GetWorldSpaceNormalizeViewDir`, то есть через `_WorldSpaceCameraPos`, который в SPI свой для каждого глаза. Текстуры экрана и глубины не используются: вода прозрачная, ZWrite Off.

² Шейдер неба: те же макросы, кроме передачи instance ID во фрагментную программу. Она там не нужна, так как фрагмент зависит только от направления взгляда.

Подавление мелких волн по `ddx`/`ddy` в SPI вычисляется для каждого глаза отдельно. Ракурсы глаз почти совпадают, поэтому заметной разницы между глазами нет.

**Методика замера производительности.**
- **Инструмент.** `FrameTimingCapture` (объект `PerfCapture`), запуск — F8.
- **Что пишется для каждого кадра:**
  - время кадра CPU и GPU (`FrameTimingManager`; требуется Player Settings → Frame Timing Stats);
  - реальный интервал кадра;
  - число вызовов отрисовки, SetPass и батчей (`ProfilerRecorder`).
- **Условия замера:**
  - сцена BridgeScene, пресет «волнение», судно на стопе;
  - голова в фиксированном положении: на рабочем месте, взгляд вперёд по носу;
  - прогрев 2 с, затем 30 с;
  - 3 прогона на режим.
- **Файлы.** `ThesisData/Performance/frametiming_<режим>_<дата>.csv` — покадрово. `frametiming_summary.csv` — сводка по замерам: среднее, медиана, p95, p99, доля кадров дольше 11,1 мс × 1,05.
- **Контроль.** Frame Debugger: в SPI вызовы помечены как stereo instanced, их вдвое меньше. Profiler → GPU Usage — если `FrameTimingManager` вернёт 0 для GPU.

Для итоговой таблицы ВКР желательно по 3 прогона на режим в одном пресете при одном ракурсе. Счётчик Draw Calls через `ProfilerRecorder` в редакторе недоступен (−1); при необходимости число вызовов берётся из Frame Debugger.

**Ограничения методики.** В Play Mode редактор дополнительно рисует окно Game и интерфейс редактора, поэтому абсолютные значения выше, чем в сборке. Корректно сравнивать только режимы между собой при одинаковых условиях. Virtual Desktop кодирует видео на том же GPU (аппаратный кодер). Это может влиять на общую загрузку, поэтому оба режима измеряются при одинаковых настройках Virtual Desktop: разрешение, битрейт, кодек.

### 1.2. Дождь в шторм

**Что сделано.** Компонент `RainEffect` переписан и подключён к `WeatherController`. Дождь идёт только в пресете «шторм», появляется и исчезает плавно вместе со сменой погоды и не проникает в рубку.

**Связь с погодой.** В пресет погоды добавлен параметр интенсивности дождя R ∈ [0; 1]: шторм — 1, остальные пресеты — 0. При смене пресета R интерполируется так же, как свет, туман и волнение: R(t) = R₀ + (R₁ − R₀)·s(t/τ_п), где s(x) = 3x² − 2x³ (SmoothStep), τ_п = 3 с. Частота появления капель: ṅ = ṅ_max·R.

**Привязка к судну при плавающем начале координат.** Судно неподвижно в начале сцены, а мир «течёт» мимо него. Поэтому:
- частицы считаются в мировом пространстве сцены, которое в каждый момент совпадает с горизонтальной системой судна;
- излучатель ставится над камерой каждый кадр и не является дочерним к качающемуся корпусу, иначе дождь наклонялся бы при крене;
- движение судна задаётся в скорости капель явно.

Скорость капли относительно судна:

  **v** = **v**_ветра − **v**_судна + (0, −w, 0),

- **v**_ветра = U_w·**d**_ветра. Капля быстро принимает горизонтальную скорость воздуха; направление ветра то же, что у волн (`OceanWaves.windFromDeg`).
- **v**_судна = u·**e**_нос, где **e**_нос — горизонтальная проекция оси носа.
- w — установившаяся скорость падения капли.

В результате на ходу дождь заметно сносится в корму, а при смене курса меняется угол косого дождя.

Чтобы капли приходили к наблюдателю, а не мимо, излучатель смещён против относительного ветра на **v**_гор·h/w, где h — высота излучения. Время жизни капли: t_ж = (y_кам + h − y_min)/w, где y_min = max(y_кам − Δ, y_воды).

**Защита рубки.**
- **Способ.** Модуль Trigger системы частиц уничтожает капли, попавшие в объём рубки. Объём — BoxCollider-триггер `RainShelter`, дочерний к Ship, поэтому качается вместе с рубкой. Капля долетает до крыши или окна и исчезает; снаружи за стёклами дождь виден.
- **Сравнение вариантов:**
  - Collision с коллайдерами крыши — дороже по CPU и требует коллайдеров у модели мостика; зато даёт брызги, это задел на будущее;
  - маска по буферу глубины — сложнее в SPI и при прозрачной воде;
  - триггер-объём — одна проверка «точка в коробке» на частицу, не зависит от геометрии модели.
- **Взаимодействие с XR.** Триггер на слое Ignore Raycast не мешает лучам: XRI по умолчанию игнорирует триггеры (`QueryTriggerInteraction.Ignore`).

**Порядок отрисовки.** Вода прозрачная (очередь 3000, без записи глубины), капли — 3100, то есть всегда после воды.

**Сборка.** Материал капель — ассет `Rain.mat`, а не `Shader.Find` в рантайме, иначе шейдер частиц мог быть вырезан из сборки.

**Состояние на 10.10.2026: отложено.** Логика работает: по логу при шторме дождь включается, в воздухе около 3900 из 6000 частиц, часть уничтожается объёмом рубки. Но в шлеме капли не видны ни из рубки, ни снаружи. Найдены и исправлены две причины:
1. Ошибка генерации текстуры: `Mathf.SmoothStep(a, b, t)` в Unity интерполирует между a и b, а не работает как шейдерный smoothstep, поэтому непрозрачность центра капли была 0,2.
2. Очередь отрисовки: URP сбросил очередь материала в 3000 — ту же, что у воды без записи глубины.

После исправлений `Setup Rain` ещё не перезапускался, проверка будет позже. Возможные дальнейшие шаги: проверить кадр в Frame Debugger (рисуются ли частицы), временно отключить `RainShelter`, увеличить толщину капли.

**Ограничения.**
- Плотность капель стилизована: около 0,3 капли/м³ в видимом объёме против сотен в реальном ливне. Задача — визуальный признак условий, а не физическая модель осадков.
- Снижение видимости в шторм обеспечивает туман пресета (плотность 0,025), а не дождь.
- Капли не оставляют следов на стёклах; дворников и брызг нет.
- Скорость ветра постоянна и не связана с моделью судна: ветер на дрейф пока не влияет (A2).
- Объём рубки задан коробкой и подгоняется вручную. Открытые крылья мостика, если войдут в коробку, тоже окажутся «сухими».

## 2. Стенд манёвренных испытаний (запрос 2, A3 — часть 1)

### 2.1. Выделение модели в отдельный модуль

**Что сделано.**
- Уравнения движения перенесены из компонента сцены `ShipNavigation` в класс `ShipDynamicsModel` на чистом C#. Класс не зависит от сцены, игрового цикла и Play Mode.
- Модель вместе с параметрами `ShipParameters` вынесена в отдельную сборку `VRBridge.Core`.
- Один и тот же код модели теперь используют:
  - тренажёр в реальном времени (`ShipNavigation`, шаг FixedUpdate);
  - стенд испытаний (без Play Mode);
  - автоматические тесты.

  Так исключено расхождение между «моделью для испытаний» и «моделью в шлеме».

**Проверка эквивалентности.** Тест `Refactor_MatchesLegacyStep_BitForBit` сравнивает новую модель с дословной копией прежнего шага интегрирования.
- Условия: 5 прогонов по 10 000 шагов, dt = 0,02 с, случайные команды руля от −40° до +40° (включая выход за δ_max) и положения телеграфа.
- Результат: курс, угловая скорость, скорость, угол руля и координаты совпадают точно, с допуском 0.

**Исправление, найденное при тестировании.** В прежней версии коэффициент усиления считался как K = K'·sign(u)·max(|u|, U_min)/L. При остановленном судне (|u| < U_min = 0,05 м/с) K не обнулялся, и переложенный руль медленно разворачивал судно на месте: около 6° за 10 мин при L = 150 м. Это физически неверно и противоречит самой модели (r_уст ∝ u).
- **Исправление:** K = K'·u/L по фактической скорости; U_min оставлен только в T = T'·L/U как защита от деления на ноль.
- **Область изменения:** при |u| ≥ U_min результат совпадает с прежним бит в бит, поэтому поведение на ходу не изменилось.
- **Проверка:** тест `Stopped_RudderDoesNotTurnShip` — на стопе с рулём 35° за 600 с курс меняется меньше чем на 1°.

### 3.2. Эталонная модель Mariner

Модель Абковица [13] с тремя степенями свободы: продольная u, поперечная v, рыскание r.

    m'₁₁·u̇' = X'(u', v', r', δ),
    [m'₂₂ m'₂₃; m'₃₂ m'₃₃]·[v̇'; ṙ'] = [Y'; N'](u', v', r', δ),

- X', Y', N' — полиномы до 3-й степени с 50 коэффициентами;
- m'₂₂ = m' − Y'_v̇, m'₂₃ = m'·x'_G − Y'_ṙ, m'₃₂ = m'·x'_G − N'_v̇, m'₃₃ = I'_z − N'_ṙ;
- безразмерные величины: u' = Δu/U, v' = v/U, r' = r·L/U, время t' = t·U/L.

Коэффициенты и уравнения перенесены дословно из открытой реализации MSS [1] (файл `mariner.m`, ссылка на [2]) в класс `MarinerModel` (сборка `VRBridge.Core`).

Отличия переноса от `mariner.m`:
- интегрирование RK4 с шагом dt = 0,02 с;
- знак руля: δ > 0 — правый борт, как в тренажёре;
- переключатель `PropellerAsymmetry` для постоянных членов Y'₀, N'₀ (п. 3.2.3).

Рулевая машина эталона: δ̇ = δ_зад − δ (апериодическое звено, T = 1 с), |δ̇| ≤ 5 °/с, |δ| ≤ 40°. Обороты винта постоянны, телеграфа нет. Поэтому торможение и разгон эталоном не описываются.

**3.2.1. Проверка переноса.**
- При δ = 0 и выключенной асимметрии скорость за 600 с остаётся равной U0 = 7,7175 м/с (точность 10⁻⁹), курс — нулевым.
- Без асимметрии циркуляции на ПБ и ЛБ симметричны (точность 10⁻⁶).

**3.2.2. Линеаризация и ширина линейной области.** При Δu = 0 линейная подсистема (v', r') даёт передаточную функцию Номото 2-го порядка [14]:

    r'/δ = K'·(1 + T'₃·s)/((1 + T'₁·s)(1 + T'₂·s)),   T' ≈ T'₁ + T'₂ − T'₃.

Для Mariner: **K' = 3,858; T'₁ = 5,658; T'₂ = 0,372; T'₃ = 0,889; T' = 5,141.** Линеаризация проверена численно: при δ = 0,02° установившееся r' отличается от K'·δ на 0,01 %.

Линейная область оказалась очень узкой — следствие больших нелинейных членов N'_vvr, Y'_vvr, Y'_vvv.

**Таблица 3.2. Отношение установившегося r' модели Mariner к линейному K'·δ**

| δ, ° | 0,02 | 0,1 | 0,5 | 2 |
|---|---|---|---|---|
| r'/(K'·δ) | 0,9999 | 0,998 | 0,950 | 0,689 |

Отсюда следует, что модель тренажёра с постоянным K' (линейный Номото) не может одновременно воспроизвести малые и большие перекладки (п. 3.5).

**3.2.3. Асимметрия винта.** Постоянные члены Y'₀, N'₀ (влияние винта) поворачивают судно на прямом руле со скоростью около 0,17 °/с при 15 уз. Тактический диаметр при руле 35° — 6,40L на ПБ и 6,65L на ЛБ.

Модель тренажёра симметрична, поэтому для идентификации эти члены выключены: тактический диаметр без них — 6,52L. Асимметрия — ограничение модели тренажёра (п. 3.8).

### 3.3. Расширения модели тренажёра

Добавлены в `ShipDynamicsModel` с переключателями в `ShipParameters`. По умолчанию выключены: `yawModel = Nomoto`, α' = 0, C_r' = 0.
- Прежние ассеты (`Default`, `Model45m`), сцена и тест эквивалентности A3.1 (`Refactor_MatchesLegacyStep_BitForBit`) не изменились — результат совпадает бит в бит.
- При α' = 0 ветка Норрбина тоже совпадает с Номото бит в бит (тест).

**Модель Норрбина** [15] вместо линейного Номото:

    T·ṙ + r + α·r³ = K·δ,   K = K'·u/L,   T = T'·L/U,   α = α'·(L/U)²,

в безразмерной форме T'·dr'/dt' + r' + α'·r'³ = K'·δ.
- α' ≥ 0 — модель устойчивого на курсе судна.
- Установившаяся циркуляция — корень r' + α'·r'³ = K'·δ, поэтому r' растёт с δ медленнее линейного (рис. `steady_turn_rate.svg`).

Интегрирование — экспонента с «замороженным» множителем g = 1 + α·r̄², где r̄ — середина шага (предиктор-корректор):

    r(t+dt) = K·δ/g + (r − K·δ/g)·e^(−g·dt/T).

- Схема устойчива при любом шаге.
- В установившемся режиме даёт точный корень кубического уравнения.
- Сходимость по шагу: при руле 35° и α' = 50 изменение курса за 300 с при dt = 0,02 с и dt = 0,002 с различается менее чем на 0,05° (тест).

**Потеря скорости на циркуляции:**

    du/dt = (u_зад − u)/τ − C_r'·L·r².

Обоснование формы. В уравнении продольной силы модели Абковица потерю скорости на повороте дают члены X'_vv·v'², X'_rr·r'², X'_vr·v'·r'. На циркуляции v' ∝ r', поэтому все три пропорциональны r'². В размерном виде ΔX/m = (X'/m')·L·r², откуда безразмерный коэффициент C_r'.
- Шаг точный при r = const: u(t+dt) = u* + (u − u*)·e^(−dt/τ), u* = u_зад − sign(u)·C_r'·L·r²·τ.
- Установившаяся потеря: Δu = τ·C_r'·L·r² (проверено тестом с точностью 10⁻⁶ м/с).
- Потеря только уменьшает |u| и не разворачивает ход.

В ходе тестирования найдена и исправлена ошибка. Первая версия ограничения «не разворачивать ход» обнуляла цель и при экстренном торможении (u_зад < 0 < u), и время остановки выросло в 5,4 раза. Исправленное условие срабатывает, только когда знак меняет сама потеря скорости. Тест `SpeedLoss_WithoutTurn_CrashStopUnchanged` подтверждает: без поворота торможение совпадает с исходным бит в бит.

### 3.4. Методика идентификации

Метод выходной ошибки (output error). Манёвр моделируется с кандидатными параметрами, и минимизируется среднеквадратичное расхождение с эталоном.
- Оптимизатор — симплекс Нелдера–Мида [12]: коэффициенты 1 / 2 / 0,5 / 0,5, один перезапуск из найденной точки.
- Поиск ведётся по логарифмам параметров, чтобы K', T', α' оставались > 0.
- Начальная точка — лучшая на грубой сетке K' ∈ {0,3…4,8}, T' ∈ {0,5…8}, α' ∈ {0,3…30}.
- Ручной подгонки нет: целевая функция и этапы зафиксированы в коде (`ShipCalibration`), результат воспроизводится тестом-регрессией.

**Повтор руля.** Модель тренажёра получает на каждом шаге тот же фактический угол руля δ(t), что эталон (рулевая машина без ограничения скорости на время идентификации). Подбираются параметры корпуса, а не различие рулевых машин. Эталонные манёвры записаны с шагом 0,02 с на 15 уз:
- циркуляции с рулём 10°, 20°, 35° — до поворота на 540°;
- зигзаги 10°/10° и 20°/20° — 5 перекладок.

**Последовательность.**
1. τ_u — аналитически: τ_u = m'₁₁·L/(−X'_u·U0) = **95,2 с** (линейная постоянная продольного движения при неизменных оборотах).
2. C_r' — по u(t) эталонных циркуляций при эталонном r(t) (одномерная минимизация): **C_r' = 0,806**.
3. K', T' (и α') — минимизация

       J = Σ_зигзаги (RMS Δψ / ψ_зад)² + Σ_циркуляции [(RMS r / |r_уст|)² + (RMS u / Δu_уст)²],

   где ψ_зад = 10° или 20°, r_уст и Δu_уст — установившиеся угловая скорость и потеря скорости эталона.

**Этапы** (одновременно — проверка, нужна ли нелинейная модель):
1. линейный Номото только по зигзагу 10°/10°;
2. линейный Номото только по циркуляции 35°;
3. линейный Номото по всем пяти манёврам;
4. Норрбин по всем пяти манёврам;
5. для сравнения — линеаризация Mariner без подбора (п. 3.2.2).

**Проверка метода на синтетических данных** (тест `Identification_RecoversKnownNorrbinParameters`). Эталон строится той же моделью Норрбина с K' = 2, T' = 3, α' = 10. Подбор восстанавливает их с погрешностью менее 1 % при J < 10⁻⁶.

**Анализ.**
1. **Линейный Номото не попадает одновременно в малые и большие перекладки.**
   - Подобранный по зигзагу 10°/10° (K' = 1,25) точно воспроизводит углы зарыскивания 10°/10° (0 и +6 %), но даёт тактический диаметр при 35° на 63 % меньше эталона.
   - Подобранный по циркуляции 35° (K' = 0,50) точно воспроизводит циркуляцию 35° (−1 %), но занижает углы зарыскивания 10°/10° на 82–86 % и завышает тактический диаметр при 10° на 136 %.
   - Компромисс по всем манёврам ошибается на 14–65 % почти во всех показателях.

   Причина — в эталоне эффективный коэффициент усиления r'/δ падает с ростом δ (табл. 3.2), а у линейной модели он постоянен. Это основание для перехода к модели Норрбина (требование плана: «если линейный Номото не даёт правдоподобных результатов одновременно на 10° и 35°»).
2. **Норрбин уменьшает J в 21 раз** (0,951 → 0,044). Отклонение от эталона: выдвиг и тактический диаметр — в пределах 5 % при всех углах руля; скорость на циркуляции — до 1 %; углы зарыскивания 20°/20° — до 5 %; времена поворота — до 12 %.
3. **Самопроверка.** K' = 3,48 и T' = 3,97, найденные у Норрбина, близки к аналитической линеаризации (K' = 3,86; T' = 5,14). Параметры получили физический смысл: K' — наклон кривой r'(δ) у нуля, а кубический член отвечает за насыщение на больших углах. У линейных моделей K', T' — эффективные значения, далёкие от физических (K' = 0,5…1,25).
4. **Остаточные расхождения Норрбина** структурны, а не результат недоподбора:
   - прямое смещение +16…+21 %: у модели 1-го порядка нет поперечной скорости v (угла дрейфа), траектория идёт по курсу;
   - начальная поворотливость +13 % и 1-й угол зарыскивания 10°/10° +29 % (4,12° → 5,30°, абсолютная разница 1,2°): в модели 1-го порядка нет числителя (1 + T'₃·s) — быстрой начальной реакции на руль. Кроме того, рулевые машины различаются (в эталоне апериодическое звено 1 с плюс ограничение 5 °/с, в тренажёре только ограничение).

### 3.8. Ограничения модели (выявлены калибровкой)

1. **Нет поперечной скорости (дрейфа):** прямое смещение на циркуляции +16…+37 %, траектория идёт по курсу.
2. **Модель поворота 1-го порядка:** нет T'₃ — быстрой начальной реакции; начальная поворотливость Mariner +13 %, время до 1-й перекладки у KCS −16…−26 %.
3. **Только устойчивые на курсе суда** (α' ≥ 0, линейный член +r): соотношение углов зарыскивания KCS не воспроизводится (2-й угол — до +37 %).
4. **Симметрия:** асимметрия от винта (у Mariner тактический диаметр 6,40L на ПБ против 6,65L на ЛБ) и уклонение при торможении не моделируются.
5. **Торможение, разгон, задний ход** — заглушки. У эталона Mariner постоянные обороты, натурный отчёт [4] недоступен, у KCS данных нет. Баланс тяги и сопротивления (план, п. 3) не вводился: его не по чему проверить.
6. **τ_разг Mariner** — постоянная продольного движения при n = const (95,2 с). Её использование для разгона с места — экстраполяция.
7. **Эталон Mariner — модель**, хотя и сопоставленная с натурой [3]. Прямое сравнение с натурными испытаниями [4] — после получения отчёта.
8. **Потеря скорости KCS** не калибровалась (C_r' = 0).
