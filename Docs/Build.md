# Сборка тренажёра

Пока — только **PC (Windows)**: пробная сборка, чтобы проверить окно инструктора, PiP и замер вне редактора. Автономная версия для Quest 3 — запрос 20 в Plan.md (будет дописана сюда отдельным разделом).

---

## 1. PC (Windows) — пробная сборка

### 1.1. Один раз перед первой сборкой

**а) Scripting Backend → Mono.** `Edit → Project Settings → Player →` вкладка **Windows** (значок монитора) → `Other Settings → Configuration → Scripting Backend`.
- Сейчас там стоит **IL2CPP**. Для него нужны модуль Unity «Windows Build Support (IL2CPP)» и Visual Studio с компонентом «Разработка классических приложений на C++». В `.vsconfig` проекта есть только «Разработка игр на Unity», поэтому сборка с IL2CPP, скорее всего, упадёт с ошибкой компилятора C++.
- Для PC выбрать **Mono**: он входит в редактор, ничего ставить не нужно, сборка быстрее. Для Quest (Android) IL2CPP остаётся — там он обязателен, и эта настройка у Android отдельная, её не трогаем.

**б) Уровень качества для Windows → «Low».** `Edit → Project Settings → Quality`.
- В редакторе (Play Mode) сейчас используется уровень **Low** — конвейер `Performance URP Config`. На нём сделаны все замеры (табл. 13.2, 14.1).
- По умолчанию для Windows стоит **Ultra** — другой конвейер (`Quality URP Config`) и VSync «каждый кадр». Сборка выглядела бы и работала иначе, чем в редакторе, а VSync окна на мониторе может сам давать задержки кадров.
- В таблице уровней внизу есть строка **Default**: под столбцом Windows (значок монитора) раскрыть стрелку и выбрать **Low**. Зелёная галочка в столбце Windows должна встать на строку Low. Столбец Android не трогать.

**в) XR.** `Project Settings → XR Plug-in Management →` вкладка **Windows**: включён **OpenXR**, стоит галочка **Initialize XR on Startup**. `→ OpenXR →` вкладка Windows: **Render Mode — Single Pass Instanced**; профили контроллеров — те же, что сейчас (Play Mode в редакторе берёт именно эти настройки Windows, поэтому если в Play Mode всё работает — здесь ничего менять не нужно).

**г) Список сценариев сохранён в сцене.** Библиотеку сценариев (`ScenarioRunner → scenarios`) обновляет код редактора при входе в Play Mode, в сборку попадает то, что **сохранено** в сцене.
- Открыть `BridgeScene`, войти в Play Mode и выйти.
- Если в заголовке сцены звёздочка — **Ctrl+S**.
- Выделить объект `Scenario` → в инспекторе `ScenarioRunner → Scenarios`: B2-01, B3-01, C4-01.

**д) Папка сборки** — `D:\claude\VR_BridgeTrainerTEST\build\PC\` (папка `build/` в `.gitignore`, в git не попадёт). Не класть сборку в `Program Files`: замеры пишутся рядом с exe.

### 1.2. Сборка

1. `File → Build Profiles` (в Unity 6 это бывшее окно Build Settings).
2. Слева выбрать **Windows**. Если активная платформа — Android, нажать **Switch Platform** (переимпорт текстур — несколько минут, один раз; Play Mode в редакторе после этого работает как раньше).
3. Справа:
   - **Scene List** — отмечена только `Scenes/BridgeScene` (SampleScene — без галочки);
   - **Architecture** — Intel 64-bit (x86_64);
   - **Development Build** — **выключено** (первая сборка — обычная, для проверки и замеров).
4. **Build** → папка `build\PC` → «Выбрать папку». Первая сборка — 5–20 минут (компиляция шейдеров), следующие быстрее.
5. В папке появятся `VR_BridgeTrainer_1.exe`, `VR_BridgeTrainer_1_Data\`, `UnityPlayer.dll` и др. Если сборка остановилась с ошибками — скопировать красные строки из Console.

### 1.3. Запуск

1. Как для Play Mode: на ПК запущен Virtual Desktop Streamer, шлем подключён к ПК через Virtual Desktop.
2. **Play Mode в редакторе остановить.** Для чистого замера лучше закрыть и Unity (редактор занимает GPU и память; сборке он не нужен).
3. Запустить `build\PC\VR_BridgeTrainer_1.exe` (двойной щелчок на ПК или с рабочего стола в Virtual Desktop).
4. На мониторе — окно инструктора на весь экран, в шлеме — мостик. Окно должно оставаться активным (галочка Run In Background в проекте включена, при потере фокуса программа не встаёт).
5. Выход — **Alt+F4** на клавиатуре ПК (идущий замер при выходе сохраняется с `aborted = 1`).
- Если в шлеме пусто, а на мониторе окно есть — сборка не нашла OpenXR-рантайм. Проверить в Virtual Desktop (Streamer → Settings) рантайм OpenXR — должен быть тот же, что работает с Play Mode (VDXR или SteamVR).

### 1.5. Замер в сборке (главное для хвоста D1)

Те же условия, что в табл. 13.2: B3-01 ночью, упражнение идёт; меню Y → «Замер» по 30 с в трёх режимах монитора:
1. окно инструктора **без PiP**;
2. окно инструктора + PiP;
3. зеркало.

Лучше по два замера в режиме «без PiP»: в редакторе провалы были не в каждом замере.

- Файлы — **рядом со сборкой**: `build\PC\ThesisData\Performance\frametiming_summary.csv` и покадровые `frametiming_*.csv`. В столбце `editor` — 0 (сборка), в `note` — режим монитора и планшета.
- После замеров скопировать файлы в `D:\claude\VR_BridgeTrainerTEST\ThesisData\Performance\` (только новые покадровые; строки сводки дописать в общую сводку проекта или положить её рядом как `frametiming_summary_build.csv`) — и сказать мне: разберу так же, как замер 22:55, и заполню таблицу «редактор / сборка».
- **Как читать:** если в сборке без PiP 90,0 кадра/с и нет кадров ≈ 100 мс — провалы были от редактора (Game View, цикл редактора). Если провалы есть и в сборке — разбираем профайлером (п. 1.6).

### 1.6. Если провалы есть и в сборке — профайлер

1. `File → Build Profiles → Windows`: включить **Development Build** и **Autoconnect Profiler** (Deep Profiling — **не** включать: сильно замедляет). Собрать в другую папку — `build\PC-dev\`.
2. Запустить `build\PC-dev\VR_BridgeTrainer_1.exe`. В углу окна может появиться консоль разработчика с ошибками — это нормально для Development Build.
3. В Unity: `Window → Analysis → Profiler`. Вверху слева в списке подключения (там, где «Play Mode» / «Edit Mode») выбрать сборку — `VR_BridgeTrainer_1` (localhost). Кнопка записи (●) — красная.
4. В шлеме: B3-01 ночью, режим «окно без PiP», подождать провал (рывок картинки). Нажать на паузу записи в Profiler.
5. В модуле **CPU Usage** найти на графике высокий пик (> 20 мс), щёлкнуть по нему. Внизу переключить вид **Hierarchy → Timeline**. Посмотреть, какая полоса занимает почти весь кадр:
   - `Gfx.WaitForPresentOnGfxThread` / `Gfx.PresentFrame` — ожидание вывода на монитор (синхронизация окна);
   - `XR.WaitForGPU`, `XRWaitForFrame` / `OpenXR.WaitFrame` — ожидание рантайма XR (Virtual Desktop);
   - `GC.Collect` — сборка мусора (наш код создаёт мусор);
   - `Canvas.SendWillRenderCanvases`, `Canvas.BuildBatch` — перестройка UI (окно инструктора);
   - имя нашего скрипта (`InstructorWindow.Update`, …) — наш код.
6. Сделать снимок экрана Timeline с этим кадром и сохранить запись: в Profiler кнопка сохранения (дискета) → `ThesisData\Performance\profile_<дата>.data`. Прислать снимок и имя полосы.
- Development Build сам по себе немного медленнее — цифры для ВКР брать из обычной сборки (п. 1.5), а Development — только для поиска причины.
- Так же можно записать профиль Play Mode в редакторе (в списке подключения — «Play Mode»): сравнить, на какой полосе провал там.

### 1.7. Что меняется в проекте

- Пункты а) и б) п. 1.1 меняют `ProjectSettings/ProjectSettings.asset` и `ProjectSettings/QualitySettings.asset`. Эти изменения закоммитим (это настройки сборки, а не случайные изменения Play Mode). `Assets/XR/Settings/OpenXRPackageSettings.asset` — по-прежнему не коммитить.
- Если делали Switch Platform на Windows — меняется активная платформа (`EditorUserBuildSettings`, в `Library`, в git не попадает).
- Сборку (`build/`) не коммитим.

### 1.8. Отличия сборки от Play Mode (для ВКР)
